# Этап 5: SLO-панель, тревоги, постмортемы (план)

Начат 13 ноября 2026 (grilling, решения 1–14, везде принят рекомендованный вариант). Инженерная суть из `docs/engineering-roadmap.md`: бюджет ошибок, game day. Опирается на этап 0 (SLO 99,5 %, ADR 0011) и ADR 0014 (проверки UptimeRobot). Только Лаборатория: боевой сайт снаружи никто не опрашивает (ADR 0005). Термины — `GLOSSARY.md`.

## Решения

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Что считаем сделанным | **Тревоги быстрее суток → политика бюджета → постмортемы → game day**, в таком порядке | Без быстрых тревог бюджет — бухгалтерия задним числом; политика делает бюджет значимым; постмортемы и game day проверяют, что всё это работает |
| 2 | Как тревога приходит быстрее | **Падение и восстановление адреса** — встроенная интеграция UptimeRobot с Telegram (сразу, бесплатно). **Выгорание бюджета** (burn за 1 ч ≥ 14,4 и за 6 ч ≥ 6, пороги ADR 0014) считает Лаборатория попутно после `/api/health/ready` не чаще раза в 15 минут: журнал UptimeRobot через API → расчёт `scripts/monitor/sli.mjs` → тревога | Попутный запуск уже работает (outbox, сброс демо), cron GitHub опаздывает на часы, webhook на бесплатном плане ненадёжен и burn не считает |
| 3 | Куда | **Тот же бот, отдельный чат «Дежурство»** (`TELEGRAM_ALERT_CHAT_ID`), не чат Владельца с Записями. Одна тревога на окно, повтор — не чаще раза в час, плюс «восстановлено» | Владельцу — Записи, разработчику — сбои |
| 4 | SLO-панель | **Страница статуса на GitHub Pages:** остаток бюджета за 30 дней, график burn за 1 ч и 6 ч, история тревог, ссылки на постмортемы. В админку не выносим | Страница статуса — витрина (README); Владельцу бюджет Лаборатории ничего не говорит |
| 5 | Политика бюджета | **Бюджет за 30 дней исчерпан → в Лабораторию идут только PR про надёжность**, пока остаток не станет положительным. В CI — информационная плашка «бюджет исчерпан» в отчёте PR, мерж не блокируется; исключение по решению Владельца репозитория записывается в PR | Проект ведёт один человек: жёсткий блок мешал бы чинить; видимость и записанное правило — дисциплина без самоблокировки |
| 6 | Постмортемы | **Шаблон `docs/postmortems/` без поиска виноватых:** хронология, влияние на бюджет, причина, что меняем, ссылки на PR. Пишется на каждую сработавшую тревогу быстрого выгорания и на любой сбой прода. Задним числом — два: утечка токена бота (11 ноября) и невалидный замер SLO этапа 0 | Два настоящих разбора проверяют шаблон и наполняют страницу статуса |
| 7 | Game day | **Раз в квартал, сценарий заранее.** Первый — «база Лаборатории недоступна 15 минут»: сначала механика на превью, потом на production Лаборатории по объявлению, с осознанной тратой бюджета. Проверяем: тревога не позже 20 минут, страницы — наша 500, не чужая, восстановление — само | Тревога, которая ни разу не срабатывала, не проверена; бюджет и нужен, чтобы тратить его осознанно |
| 8 | Когда код | **Сразу после мержа плана, раньше П2:** миграций нет, замеры П1 не задеты (проверка — раз в 15 минут, один запрос к API UptimeRobot) | Порядок карты «2 → 5» меняется только для этапа без схемы; записано в ADR 0028 |
| 9 | Как тревога не дублируется | **Через очередь уведомлений (outbox, ADR 0017) отдельным типом** `alert.*` с ключом окна: перед постановкой — проверка, нет ли события того же ключа за последний час. Отправщик ведёт `alert.*` в чат «Дежурство». Повторы и «недоставленные» — как у Записей. Новой таблицы нет (уточнено при оформлении: вместо отдельного состояния тревог) | На Vercel несколько экземпляров: состояние в памяти дало бы дубли, новая таблица — миграцию |
| 10 | Ключ UptimeRobot в Лаборатории | **Ключ «только чтение»** (`UPTIMEROBOT_READ_KEY`), передаётся при выкатке из секретов GitHub, как `TELEGRAM_*` (`lab.yml`, `vercel deploy --env`). Ключ на запись остаётся только в `monitor.yml` и у разработчика | Процессу сайта не нужно менять мониторы |
| 11 | Что, если API UptimeRobot недоступен | **Тревога «мало данных»:** две проверки подряд без ответа API или окно с данными меньше 75 % (правило ADR 0014) → одно сообщение «мониторинг слеп», не чаще раза в 6 часов | Тишина не должна выглядеть как «всё хорошо» |
| 12 | Измерения | Время от сбоя до тревоги на game day: **≤ 20 минут** (было: до суток). Ложных тревог за неделю: **0**. Постмортемов: **2** задним числом + каждый новый. Остаток бюджета виден на странице статуса | DoD этапа |
| 13 | Прод | **Не мониторим и не трогаем** (ADR 0005, замороженный `v1.0.0`) | Ограничение проекта |
| 14 | Решения | **ADR 0028** — тревоги попутно из Лаборатории через outbox, политика бюджета, этап раньше П2 | Чтобы изменение порядка карты и путь тревог были записаны |

Решения оформлены в ADR [0028](../adr/0028-burn-alerts-piggyback-outbox.md).

## Список PR (черновик)

Каждый PR — короткая ветка, мерж только по слову Владельца репозитория. Код — сразу, раньше П2.

1. **Тревоги выгорания** — код сделан 13 ноября (включится, когда появятся секреты `UPTIMEROBOT_READ_KEY` и `TELEGRAM_ALERT_CHAT_ID`): попутная проверка раз в 15 минут (`src/app/burn-kick.ts`), журнал UptimeRobot по ключу «только чтение», расчёт `sli.mjs`, события `alert.*` в outbox с ключом окна, отправка в чат «Дежурство»; «мониторинг слеп»; `lab.yml` передаёт ключ и чат. Тесты: пороги, дедупликация, маршрут чата.
2. **Telegram UptimeRobot** для падений адресов (настройка в `uptimerobot-setup.mjs` или runbook, если API бесплатного плана не даёт).
3. **SLO-панель:** остаток бюджета, графики burn, история тревог, постмортемы — в `scripts/monitor/report.mjs` и странице статуса.
4. **Политика бюджета** — сделана 13 ноября (`docs/runbooks/error-budget.md`, задача CI `budget`); бюджет на этот день уже исчерпан (−153 %) и политика вступила в силу: `docs/runbooks/error-budget.md`, информационная плашка в CI.
5. **Постмортемы** — сделаны 13 ноября: шаблон и три разбора (`docs/postmortems/`), два задним числом и один открытый — о медленных страницах, исчерпавших бюджет: шаблон и два разбора задним числом.
6. **Game day:** сценарий «база недоступна» — превью, затем production Лаборатории; постмортем по итогам; ретро этапа.
