# Клуб по адресу запроса и кэш страниц по Клубу

Статус: proposed (11 ноября 2026, grilling; `docs/stages/stage-p2-tenancy.md`, решения 3, 7–10, 12).

У каждого Клуба свой адрес. Главная — статическая страница с ревалидацией (этап 7), кэш у неё по пути: два Клуба на одном `/ru` получили бы одну страницу. `headers()` в странице сделал бы её динамической.

## Решение

- **Карта адресов — переменная `CLUB_HOSTS`** (`адрес=idКлуба,…`), разбирает чистая функция `clubForHost` в middleware, без базы. Неизвестный адрес — Клуб `club`. Нет переменной — все адреса у Клуба `club` (прод).
- **Вне production** адрес вида `<idКлуба>--…` выбирает Клуб — для превью и локальной разработки.
- **Страницы сайта** middleware переписывает под сегмент Клуба (`/ru` → `/_c/<id>/ru`, снаружи адрес прежний): ISR-кэш свой у каждого Клуба, `revalidateSite(clubId)` сбрасывает только свой. Входящий путь `/_c/…` — 404.
- **Действия, API, кабинет, админка** читают Клуб из заголовка `x-club-id`, который ставит middleware (входящий стирает).
- **Адрес для поиска** — первый адрес Клуба в `CLUB_HOSTS`, иначе `SITE_URL`.

## Considered Options

- **Префикс в пути (`/c/iron/ru`).** Не «домен на Клуб» и ломает адреса Athletic's Gym.
- **Адреса в базе, middleware читает базу.** Запрос на каждый ответ или кэш, растущий от произвольного заголовка Host; адрес всё равно настраивается в DNS и Vercel.
- **Cookie с Клубом.** Поисковик и ссылка из WhatsApp её не несут.

## Consequences

- Новый адрес Клуба — правка переменной окружения и алиаса, без кода.
- Страницы ошибок без базы (404, 500, 503) по-прежнему показывают Клуб по умолчанию (решение 20 П1).
- Новый маршрут сайта должен жить под сегментом Клуба; тест сверяет список маршрутов.
