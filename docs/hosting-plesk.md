# Сайт на hoster.kz (Plesk): настройка, перенос, переключение, откат

Пошаговая инструкция для этапа 8 (решение — `docs/adr/0004-hosting-plesk-kz.md`). Хостинг: тариф «Эконом-1» — 256 МБ памяти, 1 vCPU, 1 ГБ диска, Plesk, Node.js 23, MariaDB 10.4, домен athleticsgym.kz. SSH и внешнего доступа к базе нет — всё делается в панели Plesk.

> **Пароли и ключи в чат не пишите.** Всё секретное вводится только в Plesk: пароль базы, `AUTH_SECRET`, строка подключения.

**Переключение сделано 16 октября 2026**: боевой сайт — https://athleticsgym.kz, `athletics-gym.vercel.app` перенаправляет на него. Supabase и прежний деплой сайта на Vercel (`athletics-meaawsu1l-korolmos-projects.vercel.app`) — резерв для отката (раздел 9) до 15 ноября: их не трогаем. Разделы 1–8 — как это делалось; пригодятся, если сайт придётся поднимать заново.

## Как это устроено

```
/var/www/vhosts/athleticsgym.kz/      ← домашняя папка (в Менеджере файлов — «/»)
├── app/                ← приложение: сюда Plesk выкладывает ветку deploy из GitHub
│   ├── start.cjs       ← файл запуска: сначала миграции базы, потом сайт
│   ├── server.js, .next/, node_modules/, prisma/migrations/
│   ├── public/         ← корневой каталог документов: картинки отдаёт сам веб-сервер
│   └── tmp/restart.txt ← изменение этого файла перезапускает приложение
├── media/              ← Фото, загруженные в админке (MEDIA_DIR). Выкатка эту папку не трогает
└── httpdocs/           ← папка Plesk по умолчанию, сайту не нужна
```

- По ручному запуску с релизным тегом (с 17 октября 2026; до этого — после каждого merge в `main`) GitHub Actions собирает сайт и кладёт готовые файлы в ветку `deploy` (`.github/workflows/deploy.yml`, `docs/runbooks/release.md`). Исходников и секретов в ней нет.
- Plesk забирает ветку `deploy` в папку `app` и перезапускает приложение. При запуске `start.cjs` сам применяет новые миграции базы — новый код не начнёт отвечать, пока схема не обновлена.
- Все секреты — только в переменных среды Plesk (раздел «Node.js»).

## 1. База данных и пользователь

1. Plesk → **Сайты и домены** → athleticsgym.kz → **Базы данных** → **Добавить базу данных**.
2. **Имя базы данных** — например `athletics` (Plesk может добавить к нему префикс — запишите полное имя, как оно показано в списке).
3. **Сервер баз данных** — MariaDB, `localhost:3306`.
4. **Пользователь базы данных**: имя — например `athletics`; пароль — **только латинские буквы и цифры** (длинный, от 20 знаков): кнопка **Сгенерировать** даёт и спецзнаки — перегенерируйте или впишите свой из менеджера паролей. Тогда в строке подключения ничего не нужно кодировать (таблица ниже — на случай, если спецзнаки всё же есть). Скопируйте пароль себе в надёжное место (менеджер паролей). В чат не пишите.
5. Галочку «Пользователь имеет доступ ко всем базам данных» **не** ставьте. **ОК**.

Строка подключения для шага 2 собирается так:

```
mysql://ИМЯ_ПОЛЬЗОВАТЕЛЯ:ПАРОЛЬ@127.0.0.1:3306/ИМЯ_БАЗЫ
```

**Адрес — `127.0.0.1`, не `localhost`.** Plesk показывает сервер как `localhost:3306`, но с `localhost` Prisma до MariaDB на hoster.kz не достучалась — сайт отдавал 500; с `127.0.0.1` работает.

**Важно про пароль.** Если в пароле есть знаки `@ : / ? # % & + =` или пробел, в строке их нужно заменить кодами, иначе строка «сломается»:

| Знак | Код | Знак | Код |
|---|---|---|---|
| `@` | `%40` | `%` | `%25` |
| `:` | `%3A` | `&` | `%26` |
| `/` | `%2F` | `+` | `%2B` |
| `?` | `%3F` | `=` | `%3D` |
| `#` | `%23` | пробел | `%20` |

Остальные знаки (`! * ( ) _ - . ~` и т. п.) оставляйте как есть. Проще всего — сгенерировать пароль ещё раз, пока не получится без этих знаков.

## 2. Node.js: приложение, папки и переменные среды

### 2.1. Папки

**Менеджер файлов** (Сайты и домены → athleticsgym.kz → **Файлы**): в корне («/») создайте две папки — **`app`** и **`media`** (кнопка «+» → «Создать каталог»).

### 2.2. Включить Node.js

Сайты и домены → athleticsgym.kz → **Node.js** → **Включить Node.js**. Заполните:

| Поле | Значение |
|---|---|
| Версия Node.js | **23.11.1** |
| Диспетчер пакетов | npm |
| Корневой каталог документов | **/app/public** |
| Режим приложения | **production** |
| Корневой каталог приложения | **/app** |
| Файл запуска приложения | **start.cjs** |

Кнопку **NPM install** («Установка NPM») **не нажимать никогда**: все пакеты уже лежат в сборке. На hoster.kz стоит CloudLinux — он по этой кнопке заменяет папку `/app/node_modules` своей (ссылкой на виртуальное окружение), и сайт падает с «Cannot find module». По той же причине **не выключайте и не включайте Node.js** без нужды — для перезапуска есть **Перезапустить приложение**. Если «Cannot find module» всё же появился — см. «Частые проблемы».

### 2.3. Переменные среды

Там же, **Пользовательские переменные среды** → «Указать» / «+». Добавьте по одной:

| Переменная | Значение | Зачем |
|---|---|---|
| `DATABASE_URL` | строка из шага 1 | база |
| `AUTH_SECRET` | случайная строка от 48 знаков (как получить — ниже) | подпись входа в админку |
| `APP_ENV` | **`staging`** до переключения, **`production`** при переключении | индексация поисковиками и защита seed |
| `SITE_URL` | `https://athleticsgym.kz` | адрес сайта в ссылках, sitemap, превью |
| `NODE_OPTIONS` | `--max-old-space-size=160` | предел памяти под 256 МБ тарифа |
| `STORAGE_DRIVER` | `local` | Фото — на диске хостинга |
| `MEDIA_DIR` | `/var/www/vhosts/athleticsgym.kz/media` | папка Фото (путь — из шапки Менеджера файлов; если отличается — свой) |
| `GOOGLE_SITE_VERIFICATION` | не задаём: сайт подтверждён в Search Console через DNS (ресурс «Домен») | подтверждение сайта в Google способом «Тег HTML» — только если понадобится ресурс «Префикс URL» |

Необязательные:

- `MEDIA_QUOTA_MB` — лимит общего объёма Фото в МБ, по умолчанию 500. Диск 1 ГБ делят приложение (~115 МБ), копия репозитория Git в Plesk, кэш страниц, логи и Фото.
- `MIGRATE_ON_START=0` — не применять миграции при запуске (тогда — вручную, см. «Миграции»).
- `ADMIN_LOGIN` / `ADMIN_PASSWORD` — нужны, **только если** в базе ещё нет Аккаунта Владельца. После импорта дампа (шаг 4) аккаунт уже есть — Владелец входит со своим нынешним паролем, эти переменные не задавайте.

**`AUTH_SECRET`** — сгенерируйте на своём компьютере в PowerShell и вставьте результат в Plesk:

```powershell
[Convert]::ToBase64String((1..48 | ForEach-Object { Get-Random -Maximum 256 }) -as [byte[]])
```

Тот же, что на Vercel, брать не нужно: при переключении все входы в админку просто попросят войти заново.

Нажмите **Применить** / **Включить**. Приложение пока не запустится — в папке `app` ещё пусто. Это нормально.

## 3. «Развернуть с помощью Git» на ветку deploy

1. Сайты и домены → athleticsgym.kz → **Git** → **Добавить репозиторий** (если Git уже настраивался для домена — «Добавить репозиторий» в списке).
2. **Удалённый репозиторий Git**: `https://github.com/korolmo/athletics-gym.git`. Репозиторий публичный — SSH-ключ не нужен.
3. **Имя репозитория** — например `athletics-gym`.
4. **Режим развёртывания** — **Автоматическое развёртывание**.
5. **Путь развёртывания** — **/app**.
6. **Включить дополнительные команды развёртывания** — галочку поставить и вписать:

   ```
   mkdir -p tmp && touch tmp/restart.txt
   ```

   Эта команда перезапускает приложение после каждой выкатки, а при запуске применяются новые миграции. `mkdir -p tmp` нужен потому, что первую выкатку Plesk делает из `main` (ветку `deploy` выбирают только на шаге 7), а в `main` папки `tmp` нет; в ветке `deploy` она есть (`tmp/.gitkeep` кладёт `scripts/standalone/assemble.mjs`). Если Plesk не даёт сохранить команды (на тарифе может не быть оболочки), оставьте поле пустым — тогда после выкатки нажимайте **Node.js → Перезапустить приложение**.
7. **ОК**. После клонирования откройте настройки репозитория (значок шестерёнки или «Настройки репозитория») и выберите **ветку `deploy`** (по умолчанию стоит `main` — в ней исходники, а не готовый сайт). Сохраните.
8. **Автоматически по пушу.** В настройках репозитория Plesk показывает **адрес веб-перехватчика (Webhook URL)**. Скопируйте его и добавьте в GitHub: репозиторий → **Settings** → **Webhooks** → **Add webhook**: Payload URL — адрес из Plesk, Content type — `application/json`, событие — **Just the push event**. Без этого шага выкатку нужно запускать в Plesk кнопкой **Получить сейчас** / **Развернуть сейчас**.

> Ветка `deploy` каждый раз перезаписывается одним коммитом без истории — так копия репозитория в Plesk не растёт. Если Plesk однажды пожалуется на «unrelated histories» или не сможет получить ветку — удалите репозиторий в Plesk (файлы в `/app` и `/media` при этом не удаляются, если не ставить галочку «удалить файлы») и добавьте заново по шагам выше.

Ветка `deploy` появится после первого merge в `main` с этапом 8 (или ручного запуска: GitHub → **Actions** → **Deploy (hoster.kz)** → **Run workflow**).

### Миграции базы

**Способ 1 — сам при запуске (по умолчанию).** `start.cjs` перед запуском сайта применяет ещё не применённые миграции из `prisma/migrations` и записывает их в таблицу `_prisma_migrations` — так же, как это делает Prisma. Два процесса не применят миграцию одновременно (блокировка в базе). Если миграция упала — приложение не стартует, а в **Node.js → Журналы** (или Сайты и домены → **Журналы**) будет написано, какая и почему; старый код к этому моменту уже остановлен, поэтому действуйте сразу (см. «Откат выкатки»).

**Способ 2 — вручную кнопкой.** Поставьте переменную `MIGRATE_ON_START=0`. Порядок выкатки тогда такой:
1. В Git-настройках Plesk временно снимите галочку дополнительных команд (чтобы выкатка не перезапускала приложение) и нажмите **Развернуть сейчас** — новые файлы лягут в `/app`, но работать продолжит прежний процесс.
2. **Node.js → Выполнить сценарий** → впишите `db:migrate` → **Выполнить**. Вывод покажет «Миграция применена: …» или «Новых миграций нет».
3. **Node.js → Перезапустить приложение.**

Миграции пишутся совместимыми со старым кодом (сначала добавляем, удаляем — следующей выкаткой; ADR 0003), поэтому короткое время старого кода на новой схеме безопасно.

## 4. Перенос данных: дамп базы и фото

Делается **непосредственно перед переключением** (раздел 7): всё, что Владелец или Посетители изменят на Vercel после выгрузки, на новый сайт не попадёт. Для пробного запуска до переключения можно сделать выгрузку сейчас и повторить её в день переключения.

### 4.1. Выгрузить (на своём компьютере)

```powershell
npm run transfer:export   # читает боевую Supabase (.env.preview) только на чтение
npm run transfer:verify   # импорт в локальную MariaDB (docker compose up -d) и сверка с Supabase
```

Файлы пишутся в **`C:\gym-transfer`** — вне папки проекта: она лежит в OneDrive, а хэш пароля Владельца в облако попасть не должен. Другую папку можно задать переменной `TRANSFER_OUT_DIR` (только вне OneDrive). В `C:\gym-transfer`:
- `athletics-dump.sql` — схема, все данные и отметка о базовой миграции. **В нём хэш пароля Владельца** — никому не пересылайте, после импорта удалите;
- `athletics-media.zip` — все Фото с уменьшенными копиями (сейчас на боевом сайте Фото нет — архив пустой);
- `manifest.json` — сколько строк в каждой таблице.

`transfer:verify` должен закончиться строкой «Всё совпадает: строки, значения, Фото, миграции.».

Проверка оставляет в Docker базу `athletics_transfer` — в ней тот же хэш пароля Владельца. После импорта в Plesk удалите её вместе с папкой `C:\gym-transfer`:

```powershell
docker exec athletics-gym-mariadb mariadb -uroot -proot -e "DROP DATABASE IF EXISTS athletics_transfer"
Remove-Item -Recurse -Force C:\gym-transfer
```

### 4.2. Импортировать дамп в Plesk

1. Сайты и домены → athleticsgym.kz → **Базы данных** → у базы `athletics` → **Импортировать дамп**.
2. Выберите `athletics-dump.sql` с компьютера (файл маленький). Галочку «Пересоздать базу данных» можно не ставить — дамп сам удаляет и создаёт таблицы сайта.
3. **ОК**. Через несколько секунд — сообщение об успешном импорте.

Если кнопки «Импортировать дамп» нет: у базы → **phpMyAdmin** → вкладка **Импорт** → «Выберите файл» → `athletics-dump.sql`, кодировка `utf-8` → **Вперёд**.

> Импорт **заменяет** все таблицы сайта в этой базе. Повторять его после запуска сайта — значит стереть всё, что появилось на новом хостинге.

### 4.3. Загрузить фото

1. **Менеджер файлов** → папка **`media`** → **Загрузить** → `athletics-media.zip`.
2. Отметьте архив → **Извлечь файлы** (или правой кнопкой → «Извлечь») → извлекать в текущую папку `media`. Внутри должны появиться папки `gallery`, `hero`, `trainer` и т. п. — **прямо в `media`**, без лишней вложенной папки.
3. Сам архив удалите.

Если архив пустой (Фото на сайте ещё не загружали) — шаг пропускается.

## 5. SSL и перенаправления

1. Сайты и домены → athleticsgym.kz → **SSL/TLS-сертификаты** → **Установить** бесплатный сертификат **Let's Encrypt**.
   - Отметьте **athleticsgym.kz** и **www.athleticsgym.kz** (галочка «Защитить wildcard-домен» не нужна).
   - Email — для уведомлений о продлении. **Получить бесплатно**. Сертификат продлевается сам.
2. Там же, в настройках SSL, включите **«Перенаправлять с HTTP на HTTPS»** (или: **Хостинг и DNS** → **Параметры хостинга** → «Постоянное SEO-безопасное перенаправление 301 с HTTP на HTTPS»).
3. **Хостинг и DNS** → **Параметры хостинга** → **Предпочитаемый домен** → **athleticsgym.kz** (без www): адрес `www.athleticsgym.kz` будет перенаправлять на него. **ОК**.

Проверка: `http://athleticsgym.kz`, `http://www.athleticsgym.kz` и `https://www.athleticsgym.kz` открывают `https://athleticsgym.kz/ru`.

### Почта на домене

Заведена 16 октября 2026, вся — в Plesk, к сайту отношения не имеет:

- **Ящики** — Сайты и домены → athleticsgym.kz → **Почта** → **Создать адрес эл. почты**. Пароли ящиков — только в менеджере паролей, в чат не пишите.
- **Веб-почта** — Roundcube: `https://webmail.athleticsgym.kz` (Почта → **Настройки почты** → Веб-почта: Roundcube).
- **DKIM** включён (Почта → **Настройки почты** → «Использовать систему защиты от спама DKIM для подписи исходящих писем»): письма подписываются, меньше попадают в спам. Если DNS домена ведёт не Plesk, запись DKIM из Plesk нужно добавить у регистратора вручную.
- **SSL** — сертификат Let's Encrypt покрывает и `mail.athleticsgym.kz`, и `webmail.athleticsgym.kz` (SSL/TLS-сертификаты → при выпуске отметить «Защитить почтовый домен» и webmail; продлевается вместе с сертификатом сайта). Почтовые программы подключаются к `mail.athleticsgym.kz` без предупреждений о сертификате.
- **Место.** Почта лежит на том же диске 1 ГБ, что сайт и Фото: задайте ящикам ограничение размера (Почта → ящик → «Размер почтового ящика») и следите за `freeOnDiskMb` в `/api/health`.
- Адреса Посетителей сайт не собирает; почта на домене Политику конфиденциальности сайта не меняет.

## 6. Резервные копии

- **В Plesk** (если раздел есть на тарифе): Сайты и домены → **Резервное копирование** → **Расписание** → раз в неделю, хранить 2 копии: **база данных, файлы сайта и почтовые сообщения** (с 16 октября почта на домене включена в копию). Внимание: копии, которые Plesk хранит на сервере, занимают тот же диск 1 ГБ — а с почтой они растут вместе с ящиками. Если в разделе есть «Удалённое хранилище» (FTP) — лучше туда.
- **Раз в неделю — к себе** (обязательно, даже если есть копии в Plesk):
  1. **Базы данных** → `athletics` → **Экспортировать дамп** → скачать файл `.sql` (или .zip) на компьютер.
  2. **Менеджер файлов** → отметить папку `media` → **Добавить в архив** → скачать получившийся `media.zip` → удалить архив на сервере (он занимает место).
  3. Хранить у себя последние 4 недели. В дампе — хэш пароля Владельца и Отзывы Посетителей: храните как документы с персональными данными.
  4. Почта в эту ручную копию не входит: её сохраняет копия Plesk (выше). Если резервного копирования на тарифе нет — важные письма держите и в почтовой программе на компьютере (IMAP к `mail.athleticsgym.kz`).

## 7. Проверка после запуска

Пробный запуск — с `APP_ENV=staging` (сайт закрыт от поисковиков) и данными из пробной выгрузки.

1. **Node.js** → статус «Запущено». Если ошибка — **Журналы**: там видно, на каком шаге остановился запуск (миграции, подключение к базе).
2. Откройте `https://athleticsgym.kz/ru` и `/kk` — тексты, Тарифы, Тренеры, Направления как на боевом сайте.
3. Войдите в админку `https://athleticsgym.kz/admin` (логин и пароль Владельца — те же, что на Vercel). Затем откройте **`https://athleticsgym.kz/api/health`** в той же вкладке — без входа он отвечает «Только для Владельца». В ответе проверьте:
   - `database.ok: true`, `database.version` — 10.4.x, **`database.strict: true`** (если `false` — база молча обрезает длинные тексты вместо ошибки; напишите в поддержку hoster.kz с просьбой включить `STRICT_TRANS_TABLES` для пользователя или сообщите разработчику), `database.lastMigration` — `20261015000000_init_mariadb` или новее;
   - `media.writable: true`, `media.dir` — ваша папка `media`, `media.freeOnDiskMb` — запас диска;
   - `memoryMb.rss` — память процесса (под нагрузкой при проверке было до ~195 МБ), `memoryMb.heapLimit` около 160–170 (значит `NODE_OPTIONS` применилась);
   - `node` — v23.11.1, `os`, `openssl` — для справки.
4. В админке → **Фото** → загрузите фото в Галерею → оно появилось на сайте; удалите его → исчезло.
5. Оставьте тестовый Отзыв на сайте (с галочкой Согласия) → в админке «Отзывы» он «Новый» → удалите.
6. Нажмите на сайте кнопку WhatsApp → на главной админки счётчик Обращений вырос.
7. `/ru/privacy` — «Данные хранятся на серверах в Республике Казахстан (hoster.kz)».
8. `https://athleticsgym.kz/robots.txt` — при `APP_ENV=staging` должно быть `Disallow: /`.

## 8. Переключение (только после «ок» владельца проекта)

Порядок — в один день, лучше вечером, когда в админке никто не работает:

1. **Заморозка.** Владелец ничего не меняет в админке Vercel до конца переключения.
2. **Выгрузка и проверка** — раздел 4.1 (свежая выгрузка), затем **импорт дампа и фото** — 4.2 и 4.3 (заменяют данные пробного запуска).
3. **Plesk → Node.js → переменные:** `APP_ENV=production`, `SITE_URL=https://athleticsgym.kz` → **Перезапустить приложение**. Проверка — раздел 7; `robots.txt` теперь разрешает индексацию и указывает `https://athleticsgym.kz/sitemap.xml`.
4. **Редирект со старого адреса.** На своём компьютере, в папке `ops/vercel-redirect` репозитория (один раз — `npx vercel link`, выбрать проект **athletics-gym**):

   ```powershell
   cd ops/vercel-redirect
   npx vercel deploy --prod
   ```

   Это выкатывает в проект Vercel страницу, которая постоянно (308) перенаправляет любой адрес `athletics-gym.vercel.app/…` на тот же путь `https://athleticsgym.kz/…`. Проверка: `/`, `/ru`, `/kk`, `/ru/privacy`, `/admin` на старом адресе отвечают 308 на тот же путь нового (главная — тоже 308, а не 200: её проверяет Search Console). Старая версия сайта в Vercel остаётся в списке деплоев — к ней можно вернуться за минуту (см. «План отката»).

   **Редирект держать минимум 180 дней — до ~14 апреля 2027, лучше год (до 16 октября 2027).** Пока Google ведёт «Изменение адреса», он должен видеть 308 со старого адреса; снятый раньше редирект возвращает старые адреса в выдачу. Проект Vercel `athletics-gym` до этого срока не удалять и не выкатывать в него ничего, кроме `ops/vercel-redirect` (или отката).
5. ✅ **Search Console — сделано 16 октября 2026**: `athleticsgym.kz` подтверждён через DNS (ресурс «Домен» — покрывает и `www`, и http/https; `GOOGLE_SITE_VERIFICATION` не нужна), sitemap отправлен, индексирование `/ru` и `/kk` запрошено, «Изменение адреса» с `athletics-gym.vercel.app` на `athleticsgym.kz` запущено. Как это делалось:
   1. https://search.google.com/search-console → **Добавить ресурс** → «Домен» → `athleticsgym.kz` → TXT-запись из Search Console добавить в DNS домена (Plesk → **Хостинг и DNS** → **DNS**, или у регистратора) → **Подтвердить**. Запасной способ — «Префикс URL» `https://athleticsgym.kz/` с **Тегом HTML**: значение `content` → в Plesk переменная `GOOGLE_SITE_VERIFICATION` → **Перезапустить приложение** → **Подтвердить**.
   2. В новом ресурсе → **Файлы Sitemap** → `https://athleticsgym.kz/sitemap.xml` → **Отправить**; **Проверка URL** → `https://athleticsgym.kz/ru` и `/kk` → **Запросить индексирование**.
   3. В **старом** ресурсе `https://athletics-gym.vercel.app/` → **Настройки** → **Изменение адреса** → новый сайт `https://athleticsgym.kz/` → **Проверить и обновить**. Google проверит редирект 301/308 с главной и подтверждённость нового ресурса.
6. **Админка:** «Сайт» → «Реквизиты» → **Место хранения данных**: если поле пустое — на сайте уже стоит текст по умолчанию «на серверах в Республике Казахстан (hoster.kz)», ничего делать не нужно. Если Владелец когда-то вписывал своё — заменить на «на серверах в Республике Казахстан (hoster.kz)» (KZ — «Қазақстан Республикасындағы серверлерде (hoster.kz)»).
7. **Через 30 дней** (15 ноября 2026) без проблем: ADR 0004 — статус «accepted»; базу Supabase поставить на паузу (Project → Settings → Pause), Vercel-проект оставить ради редиректа — минимум 180 дней — до ~14 апреля 2027, лучше год (до 16 октября 2027). TXT-запись подтверждения Search Console в DNS не удалять: без неё ресурс потеряет подтверждение.

## 9. План отката

**Откат выкатки (новый код сломал сайт на hoster.kz).** GitHub → Actions → **Deploy (hoster.kz)** → **Run workflow** с предыдущим релизным тегом, подтвердить в `production` (`docs/runbooks/release.md`) — в `deploy` вернётся прежняя сборка, Plesk её заберёт. **Re-run** старых запусков не нажимать: в них нет подтверждения. Если плохая выкатка успела применить миграцию — миграции только добавляющие, прежний код с новой схемой работает.

**Откат переезда (вернуть сайт на Vercel)** — пока Supabase и деплой Vercel не удалены (минимум 30 дней):

1. **Vercel → проект athletics-gym → Deployments** → последний деплой сайта **до** редиректа → «⋯» → **Promote to Production** (или `npx vercel rollback`). `athletics-gym.vercel.app` снова показывает сайт со старой базой Supabase — через минуту.
2. **athleticsgym.kz** временно ведём на старый адрес: Plesk → **Node.js → Отключить Node.js**, затем **Хостинг и DNS** → **Параметры хостинга** → **Тип хостинга: Переадресация** (или «Перенаправления» в разделе домена) → `https://athletics-gym.vercel.app`, 302 (временное).
3. В Search Console «Изменение адреса» в старом ресурсе — **Отменить перемещение**.
4. **Данные, появившиеся на hoster.kz после переключения, на Vercel сами не вернутся.** Перед отключением выгрузите их: Plesk → **Базы данных** → **Экспортировать дамп**. Отзывы, Обращения и правки админки за эти дни придётся перенести вручную (Отзывы — через админку Vercel «Добавить отзыв»; правки Настроек и Тарифов — повторить). Поэтому откат проще всего в первые дни.
5. Фото, загруженные на hoster.kz, — скачать папку `media` и при необходимости загрузить заново в админке Vercel.

Откат нарушает требование «сайт и данные — в РК», поэтому это временная мера на время исправления.

## Частые проблемы

| Что видно | Причина и что делать |
|---|---|
| Страница Passenger «Web application could not be started» | Node.js → Журналы. «DATABASE_URL не задана» — переменные среды; «Access denied» — пароль/пользователь в строке (коды знаков, раздел 1); «Can't reach database server» — в `DATABASE_URL` должен быть `127.0.0.1`, не `localhost` (раздел 1); «Миграция … не применилась» — сообщить разработчику, не перезапускать по кругу |
| «Cannot find module …» в журнале или Passenger не стартует после «Установка NPM» / выключения-включения Node.js | CloudLinux подменил `node_modules`. **Менеджер файлов** → `/app` → удалить `node_modules` (папку или ссылку) → **Git** → **Развернуть сейчас** (вернёт `node_modules` из ветки `deploy`) → **Node.js → Перезапустить приложение**. «Установка NPM» не нажимать |
| Сайт открывается, картинки — нет | Корневой каталог документов должен быть `/app/public` |
| «Место для фото закончилось» в админке | Лимит `MEDIA_QUOTA_MB` (500 МБ): удалить ненужные фото Галереи; не поднимать лимит, пока `/api/health` показывает мало `freeOnDiskMb` |
| После выкатки старый сайт | Не сработал перезапуск: Node.js → **Перезапустить приложение**; проверить, что в Git выбрана ветка `deploy` |
| Первый запрос после долгого простоя — несколько секунд | Passenger останавливает простаивающее приложение и запускает при первом запросе — так устроен виртуальный хостинг |
