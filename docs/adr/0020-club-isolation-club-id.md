# Изоляция Клубов: колонка `clubId` и клиент базы Клуба

Статус: proposed (11 ноября 2026, grilling; `docs/stages/stage-p2-tenancy.md`, решения 2, 4–6, 11, 19–20).

На П2 в одной Лаборатории работают два Клуба. Данные одного не должны быть видны другому ни на сайте, ни в кабинете, ни в админке. На hoster.kz одна база MariaDB 10.4, в ней нет row-level security.

## Решение

- **Одна база, `clubId` в каждой таблице Клуба**, включая дочерние (Тарифы, Окна, Записи). Общая только `LoginAttempt` (лимит входа в админку по адресу). Уникальность — внутри Клуба: телефон Клиента, логин Владельца, путь Фото.
- **Клиент Клуба `dbFor(clubId)`** — расширение Prisma: добавляет `clubId` в условие каждой операции модели и в каждую новую строку. Голый `db` импортируют только `tenant-db` и модуль `owner` (dependency-cruiser).
- **Сырой SQL** — только из списка исключений, с условием `clubId` и тестом.
- **Миграция** переносит все строки в Клуб `club`; боевой сайт остаётся одним Клубом и не меняется.

## Considered Options

- **Своя база на Клуб.** Изоляция сильнее, но на hoster.kz лишнюю базу не завести, а миграции пришлось бы гнать по каждой.
- **Своя схема на Клуб.** В MariaDB схема — та же база; минусы те же.
- **`clubId` только у корневых таблиц, дочерние — через родителя.** Меньше колонок, но каждый запрос к дочерней таблице требует соединения, и проверить его правилом нельзя.
- **AsyncLocalStorage с Клубом запроса.** Скрытая зависимость: сервис в тесте или в фоновом `after()` может остаться без Клуба.

## Consequences

- Каждый сервис получает id Клуба первым аргументом; фоновые задачи (outbox, сброс демо) проходят по Клубам.
- Вложенные записи Prisma расширение не видит — дочерней строке `clubId` ставится явно, пропуск ловит тест.
- Изоляцию держит код: доказательство — тест на MariaDB «Клуб B не видит Клуб A» по всем публичным сервисам.
