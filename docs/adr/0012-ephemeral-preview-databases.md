# Превью PR — каждое со своей эфемерной базой pr_<номер> в TiDB

До 17 октября 2026 превью и production Лаборатории работали с одной базой TiDB `athletics`. Из-за этого превью PR с новой миграцией меняло схему production Лаборатории, правки в админке превью были видны всем, а seed одного PR стирал данные другого.

**Решение.** У каждого PR — своя база `pr_<номер>` в том же кластере TiDB Cloud Starter:
- **Выкатка превью** (`lab.yml`, событие `pull_request`): `scripts/lab/preview-db.mjs prepare <номер>` соблюдает лимит, удаляет и заново создаёт `pr_<номер>`, потом миграции этого PR (`scripts/standalone/migrate.cjs`, как на хостинге) и `seed:lab`. Адрес базы получает только этот деплой (`vercel deploy --env DATABASE_URL=…`). В логах Actions он под маской.
- **Каждая выкатка — с чистой базой**: миграции с нуля проверяют PR так же, как CI на MariaDB, а недоделанная миграция или отменённый запуск не оставляют базу в сломанном состоянии. Правки в админке превью живут до следующего пуша в PR.
- **Закрытие PR** (смержен или нет): `lab-preview-cleanup.yml` удаляет `pr_<номер>`. У него та же группа concurrency, что у выкатки этого PR, поэтому недоделанная выкатка отменяется и база не воскреснет после удаления.
- **Лимит — 20 баз `pr_*`**: перед созданием новой самые старые удаляются (время создания — по таблицам в `information_schema`; база без таблиц считается самой старой). Так мусор не копится, даже если удаление при закрытии не сработало.
- **Production Лаборатории** — база `athletics` из `DATABASE_URL` проекта Vercel, только в окружении Production. Из окружения Preview переменная удалена: превью без своей базы не выкатывается (`lab.yml` пропускает его с предупреждением), а не падает молча на `athletics`.
- **Защита от ошибок:** скрипт строит имена только вида `pr_<число>`, адрес — только на `pr_*` или служебную `mysql`. Тесты: `scripts/lab/preview-db.test.ts`.

Секреты репозитория: `LAB_DATABASE_URL` (адрес кластера; база в пути неважна), `LAB_ADMIN_LOGIN`, `LAB_ADMIN_PASSWORD` (аккаунт Владельца в базах превью — тот же, что в Лаборатории).

## Considered Options

- **Одна база на всё** — дёшево, но превью меняет production Лаборатории.
- **Одна общая база для всех превью** — PR мешают друг другу (миграции, seed).
- **Branching TiDB Cloud** (ветки кластера) — даёт копию данных production; нам нужна чистая база из миграций и seed, а не копия. Это ещё и отдельный API с лимитами.
- **Переменные Vercel для конкретной ветки** (Preview + git branch) — работают только с Git-интеграцией, а Лаборатория выкатывается из CLI (ADR 0008).

## Consequences

- Превью дольше на ~1 минуту: `npm ci`, миграции и seed (bcrypt пароля Владельца) на каждый пуш.
- Адрес базы превью хранится в настройках деплоя Vercel (`--env`), а не в переменных проекта. Его видят участники команды Vercel, и это та же учётка TiDB, что у production Лаборатории. Отдельный пользователь TiDB с правами только на `pr_%` — следующий шаг, если в команде появятся другие люди.
- PR из форков превью не получают: им недоступны секреты.
- Без `VERCEL_TOKEN` выкатки нет вообще (ADR 0008), поэтому и баз превью тоже нет.
