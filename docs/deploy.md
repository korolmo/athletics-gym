# Выкатка и миграции базы

С этапа 8 (ADR 0004) сайт, база и Фото переезжают на виртуальный хостинг hoster.kz (Plesk, MariaDB 10.4). Пошаговая настройка Plesk, перенос данных, переключение и откат — **`docs/hosting-plesk.md`**. Здесь — как устроены базы, миграции и выкатка.

Схема базы меняется только миграциями Prisma (`prisma/migrations/`, в git; решение — ADR 0003, уточнено ADR 0004). `prisma db push` на боевой базе не используем.

## Какая база где

| База | Где | Кто с ней работает | Строка подключения |
|---|---|---|---|
| **Локальная** | MariaDB 10.4 в Docker (`docker-compose.yml`, порт 3307) | `npm run dev`, `npm run seed`, `npm run start:standalone` | `.env` (`DATABASE_URL=mysql://…@localhost:3307/athletics`) |
| **Тесты** | та же MariaDB, база `athletics_test`; в CI — сервис `mariadb:10.4` | интеграционные тесты (`src/lib/mariadb.integration.test.ts`) — удаляют все таблицы | `TEST_DATABASE_URL` |
| **Боевая (hoster.kz)** | MariaDB 10.4 на `127.0.0.1:3306` хостинга (в `DATABASE_URL` — `127.0.0.1`, не `localhost`), снаружи недоступна | только сайт на hoster.kz | переменные среды Plesk |
| **Боевая до переключения** | Supabase, код проекта `vrvupsqjhyhghgikboif` (Франкфурт) | сайт на Vercel, пока не выполнено переключение; `npm run transfer:*` (только чтение) | `.env.preview` |
| **Разработка до этапа 8** | Supabase `athletics-gym-dev` (`ptiiovdgxjdcpxlygnrx`) | кодом больше не используется (PostgreSQL) | `.env`, переменные с префиксом `SUPABASE_DEV_` |

- Превью Vercel отключены (`vercel.json`: `git.deploymentEnabled: false`): без MariaDB они бы падали. Ветка проверяется локально и в CI.
- Боевой сайт на Vercel работает на последнем деплое `main` до этапа 8 и не пересобирается: merge этапа 8 в `main` новый деплой на Vercel не запускает.
- Seed откажется работать на боевой базе: на хостинге задано `APP_ENV=production` (и по строке боевой Supabase).

## Команды

| Команда | Что делает |
|---|---|
| `npm run db:up` | Запускает локальную MariaDB 10.4 (Docker) |
| `npm run dev` | Локальный сайт и админка (перед запуском собирает копии картинок `public/_img`) |
| `npm run db:migrate:dev -- --name <имя>` | Создаёт миграцию из изменений `schema.prisma` и применяет её к локальной базе |
| `npm run db:migrate` / `npm run db:status` | Применяет миграции / показывает их состояние (локальная база) |
| `npm run seed` | **Удаляет** Залы, Тарифы и Тренеров, заводит заново из прайса, Настройки сайта — к начальным; аккаунт Владельца не трогает |
| `npm run build`, затем `node scripts/standalone/assemble.mjs` | Сборка standalone и готовый пакет для хостинга в `dist/hosting` (как в ветке `deploy`) |
| `npm run start:standalone` | Запуск `dist/hosting` локально, как в Plesk (`NODE_OPTIONS=--max-old-space-size=160`), порт 3100 |
| `npm run memory:check` | Замер памяти собранного сервера под нагрузкой; с `DOCKER_IMAGE=node:23-bookworm-slim` — в Linux-контейнере с лимитом 256 МБ |
| `npm run transfer:export`, `npm run transfer:verify` | Перенос данных с боевой Supabase: дамп и фото в `C:\gym-transfer` (вне OneDrive), проверка на локальной MariaDB (`docs/hosting-plesk.md`, раздел 4) |

Скриптов `db:status:prod` / `db:migrate:prod` больше нет: схема теперь под MySQL, к боевой Supabase Prisma не подключится, а к MariaDB хостинга снаружи доступа нет.

## Миграции

- **История PostgreSQL** (десять миграций с 7 по 11 октября) — в `prisma/archive/postgres-migrations/`, только для истории; Prisma их не читает.
- **Базовая миграция MariaDB** — `20261015000000_init_mariadb`: та же схема, что после PostgreSQL-миграций. Данных в ней нет: на боевую базу они приходят дампом переноса, локально — из seed.
- **Отличия от PostgreSQL**: строки — `VARCHAR(191)`, длинные тексты (описания, текст Отзыва, подзаголовок, тексты Женского зала и карточек, адреса, место хранения данных, ссылка на источник) — `TEXT`; пункты бегущей строки — JSON-массив в `TEXT` (массивов у MariaDB нет; кодирование — `settingsToRow` / `settingsFromRow` в `src/lib/domain/site-settings.ts`); кодировка `utf8mb4`, сравнение строк без учёта регистра (`utf8mb4_unicode_ci`); даты — `DATETIME(3)` в UTC.
- **На хостинге** миграции применяет `scripts/standalone/migrate.cjs` (без Prisma CLI: у Plesk нет SSH, а CLI с движками под все Linux занял бы ещё ~100 МБ). Он ведёт ту же таблицу `_prisma_migrations`, что и Prisma, — `prisma migrate status` с ним согласен. Запускается сам при старте приложения (`start.cjs`) или вручную (`db:migrate` в «Выполнить сценарий» Plesk).
- Файлы `*.sql` — всегда с концами строк LF (`.gitattributes`): от их байтов считается контрольная сумма миграции.

## Обычная выкатка

1. **Миграция** (если меняется схема): `npm run db:migrate:dev -- --name <что меняем>` на локальной MariaDB, коммит вместе с кодом.
2. **Ветка и PR.** CI: lint, typecheck, тесты (вместе с интеграционными на MariaDB 10.4), миграции и seed на чистой MariaDB, сборка и пакет для хостинга. Превью нет — проверка локально: `npm run build`, `node scripts/standalone/assemble.mjs`, `npm run start:standalone`.
3. **Merge в `main`.** GitHub Actions «Deploy (hoster.kz)» собирает пакет и перезаписывает ветку `deploy`; Plesk забирает её и перезапускает приложение; `start.cjs` сначала применяет новые миграции, потом запускает сайт.
4. **Проверка:** `/ru`, `/kk`, вход в админку, `/api/health` (с сессией Владельца).

**Порядок «сначала миграция, потом код» соблюдается сам**: новый код не отвечает на запросы, пока миграции не применены. Миграции по-прежнему пишем совместимыми со старым кодом (сначала добавляем, удаляем — следующей выкаткой).

**Откат кода** — перезапуск прежней сборки в GitHub Actions (`docs/hosting-plesk.md`, «План отката»).

**Если база недоступна.** Вход в админку отклоняется, пока база не ответит («Вход временно недоступен»): лимит попыток хранится в ней.

## Аккаунт Владельца

- Аккаунт один и хранится в базе (`Owner`): логин, хэш пароля (bcrypt), версия сессии. У базы разработки и у боевой он свой.
- **Сейчас** аккаунт есть в обеих базах, а `ADMIN_PASSWORD` в Vercel нет ни в Production, ни в Preview: пароль хранится только в базе, меняется только в разделе «Аккаунт».
- **Первый вход.** Пока записи нет, вход сверяется с `ADMIN_LOGIN` / `ADMIN_PASSWORD` и создаёт её. После этого переменные не используются. Если записи нет и `ADMIN_PASSWORD` не задан — войти нельзя никому.
- **Отзыв сессий.** Смена пароля и «Выйти на всех устройствах» увеличивают версию сессии; все выданные раньше куки перестают подходить. Переменной `AUTH_SESSION_VERSION` больше нет.
- **Владелец забыл пароль (hoster.kz).** Plesk → Node.js → переменные: задать `ADMIN_LOGIN` и новый `ADMIN_PASSWORD`; Базы данных → phpMyAdmin → таблица `Owner` → удалить запись; Перезапустить приложение; войти новым паролем (аккаунт создастся заново, все сессии погаснут); сменить пароль в разделе «Аккаунт»; удалить `ADMIN_PASSWORD` из переменных Plesk.
- **Владелец забыл пароль (Vercel, до переключения).** Сброс делает разработчик: задать в Vercel новый `ADMIN_PASSWORD` (Production), передеплоить, удалить запись в таблице `Owner` боевой базы (Supabase → Table Editor) и войти новым паролем — аккаунт создастся заново. Удаление записи гасит и все сессии. После входа сменить пароль в разделе «Аккаунт» и снова удалить `ADMIN_PASSWORD` из Vercel.
- **Превью и локальная разработка.** База разработки у них общая, поэтому аккаунт один на двоих. Если его запись удалить (например, вручную при проверке входа), локально он создастся заново из `.env`, а на превью — только если вернуть `ADMIN_PASSWORD` в переменные Preview. `npm run seed` аккаунт не трогает.

## Хранилище фото на hoster.kz (диск)

- Драйвер `STORAGE_DRIVER=local` (по умолчанию): Фото лежат в папке `MEDIA_DIR` вне папки приложения — выкатка их не трогает. По умолчанию — `media` рядом с папкой приложения.
- **Загрузка**: браузер сжимает фото и делает копии 400 и 800 px по ширине (`compressPhotoSet`), сервер выдаёт пути (`requestUpload`), браузер отправляет каждый файл `PUT /api/admin/media/<путь>` — только с сессией Владельца и со своей страницы, до 5 МБ, тип по первым байтам файла и совпадает с расширением, имя задаёт сервер, перезаписать файл нельзя, общий объём — не больше `MEDIA_QUOTA_MB` (500 МБ). Потом путь записывается в базу (`attachPhoto` проверяет, что все три файла на месте).
- **Раздача**: `GET /media/<путь>` (`src/app/media`), `Cache-Control: immutable` на год; отдаются только файлы по правилу имён Фото, путь с `..` не пройдёт.
- **Удаление**: при замене и удалении Фото удаляются и его копии; уборка брошенных загрузок — как раньше (старше часа, без ссылки из базы).
- **Картинки сайта**: оптимизатора next/image на сервере нет; `src/lib/image-loader.ts` подставляет в srcset готовые файлы — копии Фото и копии картинок `public/` из `public/_img` (их собирает `scripts/images/build-variants.mjs` перед `dev` и `build`). Новая картинка в `public/` получит копии сама при следующей сборке.

## Хранилище фото (Supabase Storage) — до переключения

Фото лежат в бакете `media` того же проекта Supabase, что и база: у базы разработки — своё хранилище, у боевой — своё. В базе хранится только путь к файлу (решение — `docs/adr/0002-supabase-storage-for-photos.md`).

**Переменные** — только для сервера, без `NEXT_PUBLIC`. Значения — Supabase → Project Settings → API своего проекта: «Project URL» и ключ `service_role`.

| Переменная | `.env` и Vercel → Preview | `.env.preview` и Vercel → Production |
|---|---|---|
| `SUPABASE_URL` | `https://ptiiovdgxjdcpxlygnrx.supabase.co` | `https://vrvupsqjhyhghgikboif.supabase.co` |
| `SUPABASE_SERVICE_ROLE_KEY` | ключ `service_role` проекта разработки | ключ `service_role` боевого проекта |

- Ключ `service_role` даёт полный доступ к проекту в обход всех правил: не коммитить, не вставлять в чаты, не давать ему имя с `NEXT_PUBLIC`.
- Адрес хранилища попадает в CSP (`img-src`, `connect-src`) и в настройки `next/image` **при сборке**: после добавления или смены `SUPABASE_URL` в Vercel нужен новый деплой.
- Без этих переменных сайт работает как раньше (картинки из `public/`), а раздел «Фото» сообщает, что хранилище не настроено.

**Бакет.** Создаётся и настраивается скриптом (повторный запуск безопасен, файлы не трогает):

| Команда | Проект |
|---|---|
| `npm run storage:setup` | разработка (`.env`) |
| `npm run storage:setup:prod` | **боевой** (`.env.preview`) |

Скрипт делает бакет `media` публичным и задаёт ограничения в самом бакете: только `image/webp`, `image/jpeg`, `image/png`, файл до 5 МБ. Он откажется работать, если `SUPABASE_URL` и `DATABASE_URL` указывают на разные проекты. То же можно сделать руками: Supabase → Storage → New bucket → имя `media`, Public bucket, File size limit 5 MB, Allowed MIME types — три типа выше.

**Как устроена загрузка.** Браузер Владельца сжимает фото (до ~1600 px, WebP) → сервер проверяет сессию, тип и размер и выдаёт подписанную ссылку на один файл с именем-uuid → браузер загружает файл прямо в хранилище → сервер записывает путь в базу и удаляет прежний файл этого места. Через функции Vercel файл не проходит.

**Уборка.** Файл без записи в базе не должен оставаться: при замене, удалении и неудачной записи он удаляется сразу. Загрузки, брошенные на полпути (закрыли вкладку, пропала связь), удаляются при следующей успешной загрузке — если файлу больше часа и на него нет ссылки из базы.

**Seed и Фото.** `npm run seed` Залы обновляет, а не пересоздаёт (Плакаты прайса сохраняются), фон первого экрана, фото Женского зала и Галерею не трогает. Тренеры пересоздаются — их загруженные Плакаты пропадают, файлы подберёт уборка.

## SEO и адрес сайта

| Переменная | Где | Зачем |
|---|---|---|
| `APP_ENV` | Plesk → Node.js (на Vercel вместо неё — `VERCEL_ENV`) | `production` — сайт открыт поисковикам; любое другое значение или пусто — закрыт |
| `SITE_URL` | Plesk → Node.js (необязательно) | Адрес сайта для canonical, hreflang, sitemap, превью ссылок и разметки. Без неё — `https://athleticsgym.kz`. Только `https://<домен>`, без пути и без слэша в конце |
| `GOOGLE_SITE_VERIFICATION` | Plesk → Node.js (необязательно) | Код подтверждения из Google Search Console (способ «Тег HTML», только значение `content`) |

- После смены переменных — Node.js → **Перезапустить приложение**.
- **В поиск попадает только production.** Если `APP_ENV` (запасная — `VERCEL_ENV`) не равна `production`, страницы отдают `noindex`, а `robots.txt` — `Disallow: /`. Заголовок `X-Robots-Tag` вычисляется при сборке: ветку `deploy` собирают с `APP_ENV=production`, поэтому на пробном запуске (`APP_ENV=staging`) поисковики останавливает `robots.txt`.
- В production `robots.txt` закрывает `/admin` и `/api` и ссылается на `sitemap.xml` (в нём `/ru` и `/kk` с hreflang).
- Картинка-превью ссылок собирается по запросу: `/ru/opengraph-image` и `/kk/opengraph-image`, 1200×630. WhatsApp и Telegram запоминают превью ссылки надолго.
- **Переезд на athleticsgym.kz** — `docs/hosting-plesk.md`, «Переключение»: `SITE_URL`, редирект со старого адреса (`ops/vercel-redirect`), новый ресурс и «Изменение адреса» в Search Console.

## Счётчик Обращений

- Сайт сообщает о нажатии на кнопку связи запросом `POST /api/contact` (`navigator.sendBeacon`). Ответ всегда пустой (204), даже если запись не удалась: переход в WhatsApp от него не зависит.
- В базе — только Канал, Источник, язык и время (`ContactClick`). IP не хранится, cookies не ставятся, сторонних сервисов нет.
- Лимит — 20 нажатий в минуту с одного адреса. Счёт ведётся в памяти сервера по хэшу адреса и в базу не пишется; у каждого экземпляра функции Vercel память своя, поэтому лимит приблизительный — он от накрутки «в лоб», а не точный учёт.
- Нажатия Владельца, пока он вошёл в админку в этом же браузере, не считаются. Чтобы проверить счётчик самому — нажимайте из другого браузера или из окна инкогнито.

## Кэш главной

`/ru` и `/kk` — статические страницы с ревалидацией (`src/app/[locale]/page.tsx`, `revalidate = 3600`).

- **Когда собирается**: при первом запросе после деплоя, не при сборке — сборке и CI база не нужна. Первый посетитель после деплоя ждёт как раньше (запрос к базе), остальные получают готовую страницу.
- **Когда обновляется**: каждое сохранение в админке (Тарифы, Тренеры, Направления, Фото, Отзывы, «Сайт») вызывает `revalidateSite()` — следующий запрос получает новую страницу. Отзыв Посетителя кэш не трогает: он не виден до публикации, а публикация — это сохранение в админке.
- **Запасной срок — час**: если правка сделана мимо админки (seed, SQL в Supabase, миграция с данными), сайт обновится сам в течение часа. Нужно сразу — сохранить любую форму в админке или сделать новый деплой.
- **Порядок с миграциями прежний**: сначала миграция, потом код. Страница собирается новым кодом при первом запросе; без применённой миграции она ответит ошибкой.
- **Что не запекается в страницу**: метка времени формы отзыва (её выдаёт сервер при открытии формы), счётчик Обращений (`POST /api/contact`), вход в админку. `robots.txt`, `sitemap.xml` и картинка-превью по-прежнему строятся по запросу.
