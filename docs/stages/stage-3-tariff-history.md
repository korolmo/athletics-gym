# Этап 3: история цен Тарифов (план)

Начат 13 ноября 2026 (grilling, решения 1–16, везде принят рекомендованный вариант). Инженерная суть из `docs/engineering-roadmap.md`: миграция expand/contract без простоя. Термины — `GLOSSARY.md`.

## Решения

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Зачем история | **Журнал цен и будущая цена.** Владелец заранее вносит «с 1 января — 18 000 ₸»: до этого дня сайт показывает прежнюю Цену тарифа, с этого дня — новую, без захода в админку в нужный день. Пометки «цена меняется» на сайте нет | Залы меняют прайс с начала месяца или года. Цене нужна своя таблица с датой — отсюда настоящий перенос колонок, а не косметика |
| 2 | Удаление старых колонок (contract) | **Правило N+2:** колонку удаляет следующий релиз после того, в котором код перестал её читать и писать. В Лаборатории — отдельный PR после недели проверки; на проде — следующим релизом по решению Владельца. Правило — в ADR 0022 и `docs/runbooks/release.md` | Откат на прежний релиз остаётся возможным: «миграции только добавляющие» уточняется, а не отменяется |
| 3 | Как доказываем «без простоя» | **Шаг CI «прежний код на новой схеме»:** база мигрируется кодом ветки, двойник собирается из `main` до ветки, смоук и нагрузочный круг идут без 5xx. Шаг остаётся в CI навсегда, для любой миграции. **И замер выкатки:** нагрузка на Лабораторию во время настоящей выкатки каждой стадии, доля ошибок — 0 | Первое ловит несовместимость до мержа; второе — «до/после» для DoD |
| 4 | Цена в Записи | **Не фиксируем:** оплаты в кабинете нет | Данные без потребителя (Абонементы и Kaspi отложены до кабинета) |
| 5 | Когда код | **После миграции П2 (конец ноября):** таблица цен рождается с `clubId` и через клиент `dbFor` | По карте этапов П2 → 3; без второй переделки |
| 6 | Модель | **Таблица `TariffPrice`:** Тариф, `price`, `priceTo` (диапазон «от–до», как сейчас), `fromDay` — день начала по поясу Клуба («2027-01-01», как исключения Тренеров), `createdAt`. Уникальность — (Тариф, `fromDay`). Действующая цена — запись с наибольшим `fromDay` ≤ сегодня Клуба. Удаление Тарифа удаляет его цены (каскад) | День, а не момент: прайс меняют «с числа»; день Клуба уже есть в коде (`src/lib/time`, пояс Клуба — П2) |
| 7 | Будущих цен сколько | **Сколько угодно**, каждая со своим днём; в админке — список с ближайшей сверху | Ограничение ничего не упрощает: правило «наибольший `fromDay` ≤ сегодня» одно |
| 8 | Что можно править | **Будущую цену** — изменить и удалить. **Действующую и прошлые** — не правим: новая цена «с сегодня» заменяет сегодняшнюю запись (та же пара Тариф + день). Прошлое — журнал | Журнал, который можно переписать, не журнал; опечатку в текущей цене исправляет цена «с сегодня» |
| 9 | Смена цены в полночь и кэш главной | **Попутная проверка** (как отправка уведомлений и сброс демо): после `/api/health/ready`, раз в 5 минут — если с прошлой проверки наступил день чьей-то цены, `revalidateSite()`. На хостинге без UptimeRobot — запасной срок кэша, час | Главная — статическая с ревалидацией (этап 7); планировщика на hoster.kz нет |
| 10 | Стадии expand/contract | **Expand:** таблица и перенос (одна цена «с дня создания Тарифа» на каждый Тариф, тест «один в один» на MariaDB), код пишет в обе стороны, читает старое. **Migrate:** чтение из новой таблицы, запись в обе. **Contract:** код перестаёт писать старые колонки, следующий релиз их удаляет | Каждая стадия — отдельный PR и отдельная выкатка; любая работает и со схемой соседней стадии |
| 11 | Старые колонки во время migrate | **Двойная запись держит `Tariff.price` = действующей цене на момент сохранения.** Будущая цена, наступившая позже, в старую колонку не попадает: прежний релиз после отката покажет цену на день последнего сохранения | Честное ограничение окна отката; записано в runbook |
| 12 | Демо-сброс (П1) | **Цены входят в снимок модуля `tariffs`** (`snapshot/restoreTariffsDemo`) | Гость может планировать цены — сброс должен их вернуть |
| 13 | Гость демо-админки | **Планировать и менять будущую цену — можно; удалять цену — нет** (`requireRealOwner`, как другие удаления) | Решение 9 П1: удаления закрыты Гостю |
| 14 | Чужие чтения цены | **Модуль `trainers` сортирует Тарифы Тренера по действующей цене через модуль `tariffs`**, а не по колонке | Иначе contract сломал бы Тренеров; заодно убывает известное нарушение границ |
| 15 | Измерения | Ошибок во время выкатки каждой стадии (нагрузка на Лабораторию): **0**. Шаг CI «прежний код на новой схеме» — зелёный на каждой стадии. Запросов к базе на главную: не больше, чем до этапа (цены — одним запросом с Тарифами). Прод-двойник: медиана пика памяти — не выше базы после П2 + 5 МБ. Будущая цена появляется на сайте не позже чем через 5 минут после полуночи Клуба (Лаборатория) | DoD этапа: «до/после» |
| 16 | Термины | **«Цена тарифа»** — цена или диапазон, действующие с дня по поясу Клуба; у Тарифа — история Цен. **«Будущая цена»** — Цена тарифа с днём позже сегодняшнего | В GLOSSARY — один термин и одно уточнение |

Решения оформлены в ADR [0022](../adr/0022-expand-contract-migrations.md) (миграции expand/contract, правило N+2, шаг CI «прежний код на новой схеме»).

## Список PR (черновик)

Каждый PR — короткая ветка, мерж только по слову Владельца репозитория. Код — после миграции П2.

1. **Шаг CI «прежний код на новой схеме»** — сделан 13 ноября, раньше П2 (только CI): задача `compat` в `ci.yml`. База мигрируется и наполняется seed кодом ветки; пакет для хостинга собирается из базы (база PR или предыдущий коммит `main`) и запускается через свой `start.cjs` на этой базе; `scripts/compat/old-code-new-schema.mjs` трижды обходит сайт, кабинет, API и проверки состояния — 5xx, обрыв или неготовая база валят шаг. Запускается, только когда меняются миграции, сам скрипт или `ci.yml`; первую проверку прошёл сам на себе. Первая настоящая миграция под ним — П2.
2. **Expand:** миграция `TariffPrice` с `clubId`, перенос действующих цен (тест «один в один» на MariaDB), двойная запись в сервисе Тарифов, чтение — по-прежнему из `Tariff`.
3. **Migrate:** чтение действующей цены из `TariffPrice` (сайт, админка, Тренеры через модуль `tariffs`), снимок демо, попутная проверка смены цены в полночь.
4. **Админка:** история цен и будущая цена в карточке Тарифа (элементы `src/app/admin/ui.tsx`), удаление будущей цены — только Владельцу.
5. **Contract, шаг 1:** код перестаёт писать `Tariff.price` / `priceTo`.
6. **Contract, шаг 2 (следующий релиз):** миграция удаляет колонки; runbook релиза — правило N+2.
7. **Закрытие:** C4 компонентов, замер «после», неделя в Лаборатории, ретро.

## Замер «до»

Снимается перед PR 2, после миграции П2: число запросов к базе на `/ru`, медиана пика памяти двойника, доля ошибок при обычной выкатке Лаборатории под нагрузкой.
