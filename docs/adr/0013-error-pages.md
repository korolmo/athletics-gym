# Страницы ошибок: 404 — global-not-found, технические работы — готовая страница из middleware, 500 — Pages Router

Страницы ошибок сверстаны 23 октября 2026 по макетам Stitch (проект 4810510334939218653; промпты — `design/STITCH-BRIEF.md`). 24 октября решение пересмотрено. Первая версия из PR #52 работала на hoster.kz, но в Лаборатории на Vercel её подменяли страницы платформы, а изначальная причина обходов оказалась записана неверно.

**Что выяснилось** (24 октября, превью Лаборатории и чистые приложения Next):
- **`notFound()` на странице Next рисует только в браузере.** Сервер отдаёт пустую оболочку `<html id="__next_error__">` с кодом 404, а текст страницы приходит скриптом. Так ведёт себя чистое приложение из трёх файлов с одним корневым layout, и в Next 15.5.27, и в 16.4.3. Два корневых layout проекта тут ни при чём, хотя первая версия этого ADR называла причиной их. Готовый HTML Next отдаёт только адресам, у которых нет маршрута.
- **Vercel подменяет ответ, когда middleware переписывает адрес с кодом ошибки.** При `NextResponse.rewrite(url, { status })` маршрутизатор Vercel не вызывает функцию страницы. На код 404 он отдаёт статическую `/404` из сборки (`X-Matched-Path: /404`), и её кэширует CDN (`X-Vercel-Cache: HIT`). На код 503 — страницу платформы «The deployment is currently unavailable». Сам Next, standalone на hoster.kz, переписывание с кодом выполняет честно, поэтому прод-двойник этого не видит. Как проверяли: без папки `src/pages` результат тот же, а без кода в переписывании Vercel отдаёт нашу страницу с кодом 200. Значит, причина — код ответа в переписывании, а не Pages Router.
- **Готовый ответ middleware Vercel не трогает.** Если middleware сам отдаёт HTML с кодом 503, Vercel его пропускает. Наша `pages/500` на Vercel тоже работает (`X-Matched-Path: /500`).

**Решение.**
- **404 — `app/global-not-found.tsx`** (флаг `experimental.globalNotFound`). Next отдаёт его любому адресу без маршрута, с кодом 404 и готовым HTML, одинаково на hoster.kz и на Vercel. Страница собирается при сборке и одна на все адреса. Поэтому в HTML лежат обе языковые версии, а нужную браузер выбирает по адресу (`/kk/…`) или по cookie (`src/lib/errors/not-found-locale.ts`). Без скриптов видна русская. CDN кэширует страницу, но ответ одинаков для любой cookie, так что перепутать языки кэш не может. Страница без базы: адрес зала берётся из начальных значений в коде, часов работы и номера на ней нет, контакты ведут в 2ГИС.
- **Адрес без языка.** Главная и документы (`LOCALE_REDIRECTS` в middleware: `/`, `/privacy`, `/terms`) переадресуются на язык из cookie с `Vary: Cookie`. Любой другой адрес (`/abc`) сразу получает 404, без переадресации: иначе у поисковика лишний шаг, а в Search Console адрес попадает в «Страница с переадресацией». Middleware переписывает такой адрес под `/ru` без кода, чтобы `abc` не попал в `[locale]` как язык, и Next отдаёт тот же `global-not-found`. Адреса с точкой (`/wp-login.php`) middleware не трогает, потому что не может отличить их от файлов в `public/`. Они получают 404 от Next пустой оболочкой: код верный, текста нет.
- **503 «Идут технические работы» — `MAINTENANCE_MODE=1`.** Middleware сам отдаёт на любой странице сайта готовую двуязычную страницу (`offlinePage("maintenance")`, `src/lib/errors/offline-page.ts`) с кодом 503, `Retry-After: 600` и `no-store`. Адрес при этом не переписывается. Админка, API и Фото работают. Номера зала на странице нет, только 2ГИС: во время технических работ база обычно и так недоступна.
- **Статическая 503 веб-сервера** — та же страница с текстом «Сайт временно недоступен», файл `public/errors/503.html` (`npm run errors:build`, тест сверяет его со словарями; подключение — `docs/hosting-plesk.md`, раздел 10).
- **500.** Статическую страницу (`/ru`, `/kk`, документы), упавшую при первой сборке в кэш, Next отдаёт из Pages Router — `src/pages/500.tsx`, с кодом 500 и мимо кэша. Ошибки в браузере и упавший layout ловит `app/global-error.tsx`. **Своей `error.tsx` у сайта нет.** Прод-двойник показал, что при сбое базы во время первой сборки Next кладёт отрисованную `error.tsx` в ISR-кэш как обычную страницу `/ru` с кодом 200. Макет 500 с кодом ошибки (`digest`) остался только в админке, где страницы динамические.
- **Админка.** Содержимое раздела обёрнуто в `<Suspense>`, поэтому её `not-found.tsx` и `error.tsx` показываются внутри шапки и меню. Код ответа — 200: это страницы только для Владельца, закрытые от индексации.
- **Смоук после выкатки.** Двойник поведения платформы не видит (ADR 0005). Поэтому `lab.yml` после каждой выкатки Лаборатории проверяет живой адрес (`scripts/lab/smoke.mjs`):
  - наши 404 по маркеру `data-error-page`, свежий адрес мимо кэша, `/abc` без переадресации и с одним HTML для любой cookie, `/api/health/ready`;
  - для PR — отдельное превью с `MAINTENANCE_MODE=1` и проверка 503.

## Considered Options

- **Middleware переписывает адрес с кодом 404/503 на свою страницу** (PR #52: `[locale]/[...rest]`, `/maintenance`, список страниц `SITE_PAGES`). На hoster.kz работало, на Vercel ответ подменяют страницы платформы. Убрано.
- **`src/pages/404.tsx`.** Vercel её показывает, но standalone Next отдаёт адресам без маршрута app-овый `_not-found`, а не её: страницы на двух платформах различались бы.
- **Один корневой layout с группами `(site)` и `(admin)`** (этап 6). Проверено: `notFound()` и с ним рисуется только в браузере. Обходы страниц ошибок это не убирает, а `<html lang>` у казахских страниц стал бы общим.
- **`notFound()` из маршрута `[...rest]`.** Код 404 верный, но без скриптов пустая страница.
- **`[locale]/error.tsx` по макету 500** — попадает в ISR-кэш с кодом 200 (см. «500»).

## Consequences

- Флаг `experimental.globalNotFound` экспериментальный (появился в Next 15.4). При обновлении Next проверять 404 смоуком и двойником.
- Новая страница в `src/app/[locale]` больше не требует записи в список: неизвестные адреса отсекает сам Next. В `LOCALE_REDIRECTS` вносится только то, что должно открываться и без языка. Что такие страницы существуют, проверяет тест.
- `src/pages` остаётся ради страницы 500. Побочный эффект: хуки `usePathname` и `useParams` типизированы как «может быть `null`».
- Страницу 404 Next собирает при сборке. Тексты и вид меняются только выкаткой, Настройки сайта на неё не влияют.
- Цена по памяти (прод-двойник, 256 МБ; фаза ошибок — 500 через `pages/500` и 404 сайта и админки):

  | RSS, МБ | `main` 07db571 | PR #52 (middleware) | global-not-found |
  |---|---|---|---|
  | Локально: пик обхода | 182,2 | 189,5 | 181,2 |
  | Локально: фаза ошибок | 156,6 | 163,2 | 158,9 |
  | CI: пик обхода / фаза ошибок | 198,1 / — | 201,8 / 173,7 | в описании PR |

  Порог — 230 МБ. В `main` упавшая статическая страница тоже шла через Pages Router (стандартный `_error` Next).
- Статическую 503 нужно один раз подключить в Plesk — только в окно выкатки по решению Владельца (боевой сайт заморожен на `v1.0.0`).

## Технический долг

- **Код 200 у страниц ошибок админки** (`<Suspense>`). Чтобы был настоящий код, `notFound()` должен рисоваться на сервере, а этого Next не делает (см. выше).
- **`src/pages` ради одной страницы 500** — пока ISR-сбой Next отдаёт через Pages Router.
- **Экспериментальный флаг** `globalNotFound`.

Пересмотреть при переходе на Next 16 (уже в долгах, `CLAUDE.md`). Если там `notFound()` начнёт отдавать готовый HTML, а `globalNotFound` выйдет из-под флага, то админке хватит обычного `not-found`, а `pages/500` можно будет проверить на ненужность. С этапом 6 (модули) это больше не связано.
