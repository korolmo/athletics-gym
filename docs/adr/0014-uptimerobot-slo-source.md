# Проверки Лаборатории делает UptimeRobot, SLO — только по страницам, холодный старт — по заголовку X-Cold-Start

Заменяет часть ADR 0011: как холодный старт входит в SLI и кто делает синтетические проверки. Решение «не прогревать» из ADR 0011 остаётся.

**Что показала неделя 17–25 октября 2026** (этап 0, `docs/stages/stage-0-foundation.md`, «Закрытие этапа»):
- Синтетика на cron GitHub Actions (`*/5 * * * *`) сделала 52 прогона вместо ~2300. Это 5–8 в сутки, медиана интервала — 201 минута.
- Поэтому каждая проверка `/api/health/ready` попадала на холодный экземпляр (медиана 1,4 с), и доступность вышла 67,9 %. Число меряло редкость cron и холодный старт, а не доступность. **Измерение невалидно.**
- Тревога требовала ≥ 18 проверок за час, а было не больше 3, поэтому за неделю она не могла сработать ни разу.
- Страницы `/ru` и `/kk` за ту же неделю: 104 из 104 ответов 200, 96 % быстрее 1 с.

## Решение

- **Проверки делает UptimeRobot** (бесплатный план), каждые 5 минут. Мониторы создаёт `scripts/monitor/uptimerobot-setup.mjs` из репозитория. Скрипт идемпотентный: сверяет мониторы по адресу, создаёт недостающие, правит отличающиеся, чужие не трогает. Ключ — секрет `UPTIMEROBOT_API_KEY` (GitHub) и `.env.lab` (локально), в вывод он не попадает. Мониторы:
  - `/ru` и `/kk` — монитор по ключевому слову: сбой, если в ответе нет `id="top"` (первый экран главной; его нельзя скрыть в админке, и его нет на страницах ошибок). Так ответ 200 со страницей ошибки или пустой оболочкой тоже считается сбоем;
  - `/api/health/ready` — по коду ответа.
- **GitHub Actions раз в сутки** (`monitor.yml`) забирает через API время ответа и журнал падений за 72 часа (`uptimerobot-fetch.mjs`). Пропущенный суточный запуск доберёт следующий. Повторы сливаются по паре «адрес, время». Потом workflow пересчитывает `status.json` и страницу статуса в ветке `monitoring` (`data/uptimerobot/ГГГГ-ММ.jsonl`). Сбой из журнала UptimeRobot — это `ceil(длительность / интервал)` неуспешных проверок подряд. Надёжность cron GitHub на SLO больше не влияет: она определяет только, когда пересчитан отчёт.
- **SLI** (`scripts/monitor/sli.mjs`):
  - доступность и скорость — по страницам `/ru` и `/kk`: успех — 200 с ключевым словом быстрее 1 с. SLO — 99,5 % за 30 дней;
  - `/api/health/ready` — диагностика: на странице статуса виден, бюджет не тратит;
  - холодный старт — отдельный SLI: первый запрос экземпляра (`X-Cold-Start: 1`) быстрее 1,5 с в 90 % случаев. Меряется сразу после каждой выкатки `main` (`cold-start.mjs` в `lab.yml` → `data/cold-start.jsonl` в ветке `monitoring`).
- **`X-Cold-Start`** ставят `/api/health/live` и `/ready`: `1` у первого ответа процесса, `0` дальше (флаг на уровне модуля, `src/lib/observability/cold-start.ts`). Только у маршрутов без кэша: у страницы из кэша CDN заголовок рассказывал бы о давнем запуске.
- **Тревоги под 12 проверок в час.** Две страницы дают 24 проверки в час. Отчёт пересчитывается раз в сутки, поэтому ищет худшее окно среди закончившихся за последние сутки (шаг 5 минут):
  - быстрое выгорание — burn за час ≥ 14,4, то есть 2 неуспешные проверки из 24;
  - медленное — burn за 6 часов ≥ 6, то есть 5 из 144;
  - окно в расчёт не берём, если в нём меньше 75 % ожидаемых проверок.
- **Мониторинг мониторинга.** Тревога и в двух случаях:
  - за сутки по любому адресу меньше 260 проверок из 288 (90 %);
  - последняя проверка старше 2 часов.

  Если не запустится сам суточный отчёт, страница статуса через 36 часов покажет, что данные устарели.
- Любая тревога делает запуск «Monitor Lab» красным, и GitHub присылает письмо. Падение страницы UptimeRobot сам сообщает письмом на почту аккаунта сразу. Telegram и постмортемы остаются на этапе 5.

## Что меняет частый опрос

Опрос раз в 5 минут сам держит функцию Vercel тёплой: экземпляр без запросов засыпает позже, чем через 5 минут. Значит, в SLO страниц холодных стартов почти не будет. Причина не в том, что сайт стал быстрее, а в том, что опрос его прогревает. Настоящий посетитель после ночи без трафика в Лаборатории получил бы холодный старт, а для прода (hoster.kz, Passenger) эти цифры ничего не говорят вовсе. Поэтому холодный старт меряется отдельно, сразу после выкатки, когда экземпляр точно новый, и заголовок это подтверждает. Тот же опрос держит тёплым и соединение с TiDB — это важно для выводов замера в ADR 0015.

## Considered Options

- **Оставить cron GitHub, но считать только успешные прогоны** — данных всё равно 2 % от плана, и все проверки холодные.
- **Прогрев отдельным cron** — та же ненадёжность расписания GitHub. К тому же прогревать — значит прятать холодный старт, а не мерить его (ADR 0011).
- **UptimeRobot с алертами сразу в Telegram** — запланирован на этап 5 вместе с постмортемами. Сейчас нужен источник данных для SLO, алерты подключаются тем же сервисом позже.
- **Отличать холодные проверки UptimeRobot по заголовку** — UptimeRobot не сохраняет заголовки ответов. Поэтому заголовок читает наш замер после выкатки, а в SLO страниц холодные старты входят честно.

## Consequences

- Цифра «67,9 %» в итогах этапа 0 не переписывается: рядом пометка, что измерение невалидно.
- Время ответа меряет UptimeRobot со своих точек опроса, а не GitHub из США. Цифры с неделей 17–25 октября напрямую не сравниваются.
- Мониторы создаются только при наличии `UPTIMEROBOT_API_KEY`: `node --env-file=.env.lab scripts/monitor/uptimerobot-setup.mjs --check`. Без ключа суточный отчёт красный («данные устарели»), и это правильно.
- Если `--check` покажет страницу «down», хотя она открывается, значит, в API перевёрнут смысл `keyword_type`. Это проверить в интерфейсе UptimeRobot («Alert when keyword not exists»).
- Боевой сайт по-прежнему никто снаружи не опрашивает (ADR 0006): скрипты отказываются работать с его адресом.
