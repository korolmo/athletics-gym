# Этап П2: несколько Клубов (план)

Начат 11 ноября 2026 (grilling, решения 1–22, везде принят рекомендованный вариант). Инженерная суть из `docs/engineering-roadmap.md`: изоляция данных, домен на Клуб, второй вымышленный Клуб. Опирается на П1: Клуб уже данные (ADR 0018). Термины — `GLOSSARY.md`.

## Решения

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Что показывает этап | **В Лаборатории два Клуба — Athletic's Gym и вымышленный «Iron Club»**: у каждого свой адрес, бренд, Залы, Тренеры, Тарифы, кабинет и админка; данные не пересекаются, это доказывают тесты. Создать Клуб из интерфейса нельзя — второй Клуб заводит seed | Инженерная суть — изоляция, а не экран создания Клубов; админка платформы — отдельный этап, если понадобится |
| 2 | Модель изоляции | **Одна база, колонка `clubId` в каждой таблице Клуба.** Сервисы ходят в базу через клиент Клуба `dbFor(clubId)` — расширение Prisma, которое само добавляет `clubId` в условие каждого запроса и в каждую новую строку | На hoster.kz одна база MariaDB 10.4, отдельных баз и схем там не завести; row-level security в MariaDB нет — изоляцию держит код, а доказывают тесты (решение 19) |
| 3 | Как сайт узнаёт Клуб | **По адресу запроса (Host).** Неизвестный адрес — Клуб по умолчанию (`club`) | «Домен на Клуб» — суть этапа; путь `/c/iron/…` и cookie — не то, что получит настоящий второй Клуб |
| 4 | Что принадлежит Клубу | **Всё, кроме лимита попыток входа в админку (`LoginAttempt`)** — он по адресу и общий. Клиент свой в каждом Клубе: тот же телефон в другом Клубе — другой Клиент со своим Согласием. Попытки входа Клиента (`ClientLoginCode`) и лимит Отзывов (`ReviewSubmission`) — по Клубу | Простая изоляция и честно с персональными данными: Клуб B не узнаёт, что человек ходит в Клуб A |
| 5 | Владелец | **Свой Аккаунт Владельца у каждого Клуба; сессия привязана к Клубу** — id Клуба входит в подписанный токен, на адресе другого Клуба сессия недействительна. Оператора платформы нет | Без интерфейса создания Клубов оператору нечего делать |
| 6 | Боевой сайт | **Общий код, без форка.** Миграция переносит все строки в Клуб `club` (тест «один в один» на MariaDB); прод при будущей выкатке остаётся одним Клубом и внешне не меняется. Выкатка — только по решению Владельца | ADR 0001: одна кодовая база; прод заморожен на `v1.0.0` |
| 7 | Карта адресов | **Переменная окружения `CLUB_HOSTS`** (`адрес=idКлуба,…`), чистая функция `clubForHost` разбирает её в middleware без базы. Нет переменной — все адреса у Клуба `club`: на проде так и останется | Адрес — настройка инфраструктуры (DNS, алиас Vercel), без неё строка в базе бесполезна; middleware работает без базы — нет запроса на каждый ответ и нет кэша на произвольный заголовок Host |
| 8 | Превью и локально | **Вне production адрес вида `<idКлуба>--…` выбирает Клуб** (`iron--pr-12-athletics-lab.vercel.app`, `iron--localhost`); `lab.yml` даёт каждому превью второй алиас для `iron`. На production правило выключено | Без этого второй Клуб не проверить на превью и на машине разработчика |
| 9 | Кэш главной | **Middleware переписывает адрес страниц сайта под сегмент Клуба** (`/ru` → `/_c/iron/ru`, снаружи адрес прежний); ISR-кэш у каждого Клуба свой, `revalidateSite(clubId)` сбрасывает только свой Клуб. Входящий путь `/_c/…` middleware отдаёт как 404 | Сейчас кэш по пути: два Клуба на одном `/ru` получили бы одну страницу. `headers()` в странице сделал бы её динамической (этап 7) |
| 10 | Клуб в действиях и API | **Middleware ставит заголовок `x-club-id` (входящий с тем же именем стирает)**; серверные действия, API и кабинет читают его через `currentClub()`. Сервисы получают id Клуба первым аргументом явно — без AsyncLocalStorage | Явный аргумент виден в коде и в тестах; подделать заголовок снаружи нельзя |
| 11 | Ключи и уникальность | **`clubId` во всех таблицах Клуба, включая дочерние** (Тариф, Окна, Записи — денормализация); уникальность — внутри Клуба: телефон Клиента, логин Владельца, путь Фото, `AboutCard` — по `(clubId, …)`. Одиночные строки (Настройки сайта, Демо) получают ключ по Клубу. У Зала поле `kind` («общий», «женский»): код опирается на него, а не на id `general` / `women` | Одинаковое правило для всех таблиц проще проверить; составные ключи не дают двум Клубам конфликтовать |
| 12 | Адрес сайта для поиска | **У Клуба основной адрес — первый его адрес в `CLUB_HOSTS`**; Клуб без адреса — `SITE_URL`, как сейчас. Canonical, hreflang, sitemap, robots и JSON-LD — по адресу Клуба; `robots` и `sitemap` строятся по Host запроса | Прод без `CLUB_HOSTS` даёт прежний `https://athleticsgym.kz` |
| 13 | Фото | **Новые файлы — в папке Клуба** (`<clubId>/gallery/<uuid>.webp`), прежние пути Клуба `club` не переносим. `PUT /api/admin/media/<путь>` принимает путь только из папки Клуба сессии; лимит `MEDIA_QUOTA_MB` — на Клуб | Перенос файлов на проде — лишний риск; проверка папки закрывает запись в чужие Фото |
| 14 | Часовой пояс | **Функции времени берут пояс Клуба**, константа `CLUB_TIME_ZONE` уходит. В форме «Клуб» пояс по-прежнему не меняется. Iron Club — в Астане (тот же UTC+5), другой пояс проверяют тесты (`Europe/Moscow`, `Asia/Tashkent`) | Решение 1 П1 отложило это до П2; смена пояса сдвигает Записи — без интерфейса |
| 15 | Уведомления | **Один бот платформы (токен — в окружении), чат — поле Клуба `telegramChatId`**; пусто у Клуба `club` — запасная `TELEGRAM_CHAT_ID`, как сейчас. В Лаборатории Iron Club пишет в тот же чат, сообщение начинается с названия Клуба | Токен — секрет платформы; чат — свойство Клуба |
| 16 | Демо-админка и сброс | **Гость входит на адресе любого Клуба и правит только его; снимок и суточный сброс — у каждого Клуба свои** (`DemoState` по Клубу), 04:00 по поясу Клуба | Решение 6 П1 сохраняется на каждый Клуб |
| 17 | Первый Владелец Клуба | **Первый вход по `ADMIN_LOGIN` / `ADMIN_PASSWORD` создаёт Владельца того Клуба, на чьём адресе вход** (как этап 1 админки). Seed Владельцев не создаёт | Пароли не попадают в seed и в git |
| 18 | Второй Клуб | **«Iron Club», Астана, голубой акцент, логотип — монограмма; один Зал, три вымышленных Тренера, Тарифы, два Направления; Отзывов нет.** Заводит `npm run seed:club iron` — только Лаборатория и локально, на `APP_ENV=production` отказывается без исключений | Вымышленный Клуб не должен появиться на проде даже по ошибке |
| 19 | Как проверяем изоляцию | **Три слоя:** (1) dependency-cruiser — голый `db` из `@/lib/db` импортируют только `tenant-db` и модуль `owner` (ради `LoginAttempt`); (2) тест каждого модуля — сервисы ходят только через `dbFor`, сырых запросов (`$queryRaw`, `$executeRaw`) вне списка исключений нет; (3) тест на MariaDB «Клуб B не видит Клуб A»: два Клуба с данными, каждый публичный сервис каждого модуля вызывается от B, ни одного id A в ответе, ни одной записи A не изменено | Код — единственная защита (решение 2), значит, проверка должна покрывать все пути к базе |
| 20 | Что в `dbFor` | **Все операции модели** (`find*`, `count`, `aggregate`, `groupBy`, `create*`, `update*`, `upsert`, `delete*`); во вложенных записях дочерняя строка получает `clubId` явно (тест ловит пропуск); `$transaction` — через клиент Клуба. Сырые запросы (сейчас 13 мест с `$queryRaw` / `$executeRaw` / `$transaction`) — переписать или внести в список исключений с условием `clubId` и тестом | Расширение Prisma не видит вложенных записей и сырого SQL |
| 21 | Измерения | Таблиц Клуба с `clubId`: **0 → 19 из 21**. Утечек между Клубами в тесте на MariaDB: **0** по всем сервисам (число сервисов — в отчёте). Кода, чтобы завести Клуб: **seed, 0 строк кода**. JS `/[locale]` **≤ 125 kB**. Прод-двойник: **медиана пика памяти ≤ 205 МБ**, медиана p95 — не хуже разброса «до» (`scripts/twin/history.mjs`). Смоук `lab.yml` — на обоих адресах | DoD этапа: «до/после» |
| 22 | Когда | **PR 1 (чистые функции адресов) — сразу. Миграция и перевод сервисов — после закрытия П1 (~24 ноября)**: на неделе П1 идут замеры сброса и памяти двойника, миграция на 21 таблицу их бы смешала | Неделя этапа 1 до ~17 ноября, затем неделя П1 с гостевым входом |

Решения оформлены в ADR: [0020](../adr/0020-club-isolation-club-id.md) (изоляция Клубов колонкой `clubId` и клиентом Клуба), [0021](../adr/0021-club-by-host.md) (Клуб по адресу запроса и кэш по Клубу).

## Список PR (черновик)

Каждый PR — короткая ветка, мерж только по слову Владельца репозитория.

1. **Адрес → Клуб**: `CLUB_HOSTS`, `clubForHost`, правило `<idКлуба>--` вне production, основной адрес Клуба — чистые функции и тесты; поведение не меняется.
2. **Миграция expand**: `clubId` со значением `club` во всех таблицах Клуба, внешние ключи на `Club`, составные уникальные ключи, `Hall.kind`, ключи одиночных строк; тест «один в один» на MariaDB; `telegramChatId` у Клуба.
3. **Клиент Клуба** `src/lib/tenant-db.ts` (`dbFor`), правило dependency-cruiser и тест «только `dbFor`»; перевод сервисов — тремя PR: (а) `club`, `site`, `photos`, `legal`, `home`, `demo`; (б) `tariffs`, `trainers`, `directions`, `reviews`, `contacts`; (в) `owner`, `clients`, `schedule`, `bookings`, `notifications`. Сырые запросы — переписать или в исключения.
4. **Клуб в запросе**: middleware — Host → Клуб, переписывание под `/_c/<id>/…`, заголовок `x-club-id`; `currentClub()`; `revalidateSite(clubId)`; SEO, sitemap, robots, картинка-превью — по Клубу.
5. **Сессии и Фото по Клубу**: id Клуба в токенах Владельца, Гостя и Клиента; папка Клуба у Фото, проверка пути в `PUT`, лимит на Клуб; первый Владелец Клуба по `ADMIN_LOGIN`.
6. **Пояс, уведомления, сброс по Клубу**: функции времени с поясом Клуба, чат Клуба, `DemoState` и сброс на каждый Клуб.
7. **Iron Club**: `seed:club iron`, второй адрес Лаборатории и алиас превью в `lab.yml`, тест «Клуб B не видит Клуб A» на MariaDB, смоук на обоих адресах.
8. **Закрытие**: C4 (контекст и компоненты), замер «после», runbook «Новый Клуб», неделя в Лаборатории, ретро.
