# Выкатка и миграции базы

Схема базы меняется только миграциями Prisma (`prisma/migrations/`, в git; решение — `docs/adr/0003-prisma-migrate.md`). `prisma db push` на боевой базе не используем.

## Какая база где

| Файл | На какую базу смотрит | Для чего |
|---|---|---|
| `.env` | Локальная или тестовая | Повседневная работа: `npm run dev`, `npm run db:migrate:dev`, `npm run seed` |
| `.env.preview` | **Боевая** (Supabase, Франкфурт) — она же база превью | Только команды выкатки, с явным указанием файла |

**Локальный `.env` на боевую базу не переключаем — ни временно, ни насовсем.** Команды для боевой базы запускаются с явным файлом окружения, и каждая сначала показывает, к какой базе подключилась (`Datasource "db": … at "…"`). Перед тем как продолжать, сверьте хост: боевой — `…eu-central-1.pooler.supabase.com`.

## Команды

| Команда | Что делает | База |
|---|---|---|
| `npm run db:migrate:dev -- --name <имя>` | Создаёт миграцию из изменений `schema.prisma` и применяет её | из `.env` (локальная/тестовая) |
| `npm run db:migrate` | Применяет ещё не применённые миграции | из `.env` |
| `npm run db:status` | Показывает, какие миграции применены | из `.env` |
| `npm run seed` | **Удаляет** Залы, Тарифы и Тренеров и заводит заново из прайса | из `.env`; на боевой откажется |
| `npm run db:status:prod` | Состояние миграций боевой базы (только чтение) | **боевая**, из `.env.preview` |
| `npm run db:migrate:prod` | Применяет миграции к боевой базе | **боевая**, из `.env.preview` |

Скрипты `:prod` — это `dotenv -e .env.preview -- prisma …` (пакет `dotenv-cli`): переменные из `.env.preview` подставляются только на время одной команды. То же без `dotenv-cli`, одной командой PowerShell:

```powershell
# переменные живут только внутри этого вызова и не остаются в окне терминала
powershell -NoProfile -Command "Get-Content .env.preview | Where-Object { $_ -match '^\s*(DATABASE_URL|DIRECT_URL)\s*=' } | ForEach-Object { $k, $v = $_ -split '=', 2; Set-Item ('Env:' + $k.Trim()) $v.Trim().Trim([char]34) }; npx prisma migrate status"
```

Seed на боевой базе по умолчанию не запустится: он узнаёт её по строке подключения и завершится с объяснением. Осознанный запуск — `npx dotenv -e .env.preview -- npm run seed:force-production`; он сотрёт всё, что Владелец поправил в админке.

## Миграции

| Миграция | Что в ней |
|---|---|
| `20261007000000_init` | Базовая (baseline): схема этапа 0 — Залы, Тарифы, Тренеры. На боевой базе уже есть, её нужно только **пометить** применённой. |
| `20261008000000_login_attempts` | Новая таблица `LoginAttempt` — неудачные попытки входа в админку (лимит перебора пароля). Существующие таблицы не трогает. |

## Выкатка ветки `refactor-security` на production — один раз

Превью и боевой сайт сейчас на одной базе, поэтому шаги 2–3 меняют боевую базу. Они только добавляют: создают служебную таблицу миграций и пустую таблицу `LoginAttempt`. Текущий код на них не смотрит, сайт во время шагов работает.

1. **Посмотреть состояние** (только чтение) и сверить хост в первой строке вывода:
   ```powershell
   npm run db:status:prod
   ```
   Ожидаемо до baseline: хост `…eu-central-1…`, две миграции не применены.
2. **Baseline** — сказать Prisma, что базовая схема уже на месте (данные не меняются):
   ```powershell
   npx dotenv -e .env.preview -- prisma migrate resolve --applied 20261007000000_init
   ```
3. **Применить новые миграции:**
   ```powershell
   npm run db:migrate:prod
   ```
   Ожидаемый вывод: `Applying migration 20261008000000_login_attempts`, затем `All migrations have been successfully applied`.
4. **Проверить:** `npm run db:status:prod` → `Database schema is up to date!`
5. **Merge PR в `main`** и production-деплой.
6. **После деплоя:** войти в админку заново (формат куки сессии изменился, старые входы недействительны) и проверить `/ru`, `/kk`.

**Порядок обязателен: сначала миграция (шаги 1–4), потом код (шаг 5).** Коммит «Лимит входа: ошибка базы = отказ во входе» убирает запасной режим «таблицы нет → лимит выключен». Если выкатить его на базу без таблицы `LoginAttempt`, сайт будет работать, но войти в админку не сможет никто — форма ответит «Вход временно недоступен». То же относится к превью: до шага 3 войти в админку на превью этой ветки нельзя.

Если так всё же случилось: применить миграцию (шаги 1–4) — вход заработает без передеплоя.

**Откат.** Код — «Promote» предыдущего деплоя в Vercel. Базу откатывать не нужно: старый код новую таблицу не замечает.

**Если база недоступна.** Вход в админку отклоняется, пока база не ответит (лимит попыток хранится в ней). Уже вошедший Владелец тоже ничего не сможет открыть — данные админки в той же базе.

## Обычная выкатка дальше

1. Изменили `schema.prisma` → `npm run db:migrate:dev -- --name <что меняем>` на локальной или тестовой базе → миграция появилась в `prisma/migrations/` → коммит вместе с кодом.
2. PR, проверки CI, превью.
3. Перед merge: `npm run db:status:prod`, сверить хост и список, затем `npm run db:migrate:prod`; после этого merge и деплой. Миграции пишем так, чтобы старый код продолжал работать с новой схемой (сначала добавляем, удаляем — следующей выкаткой).

## Что стоит сделать позже

- Отдельная база для превью: сейчас проверка превью меняет боевые данные, а миграцию нельзя обкатать на превью до production. Тогда же переименовать `.env.preview` в `.env.production`, а в `.env.preview` положить строки базы превью.
- После этого `prisma migrate deploy` можно добавить в сборку Vercel, чтобы миграции применялись автоматически. Пока база общая, это опасно: любой пуш в ветку применил бы миграции к боевой базе.
