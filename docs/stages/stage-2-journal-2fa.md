# Этап 2: журнал действий и двухфакторный вход (план)

Начат 13 ноября 2026 (grilling, решения 1–17, везде принят рекомендованный вариант). Инженерная суть из `docs/engineering-roadmap.md`: доменные события, append-only журнал, TOTP. Термины — `GLOSSARY.md`.

## Решения

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Что пишет журнал | **Изменения данных и события безопасности.** Изменения: что, над чем, кто (Владелец или Гость), когда; у правок — изменённые поля «было → стало». События безопасности: вход, выход, неудачная попытка, смена пароля, «Выйти на всех устройствах», включение и выключение 2FA, вход по коду восстановления. Просмотров нет. Телефоны Клиентов не пишем — только id Записи и маску | Это спросят, если что-то пропало или кто-то вошёл; просмотры — шум и персональные данные без пользы |
| 2 | Как событие попадает в журнал | **Доменное событие в той же транзакции, что и изменение:** модуль-хозяин вызывает `recordEvent(tx, …)` модуля `journal`, как `enqueue` у outbox (ADR 0017). Нет изменения — нет записи | «Тариф: цена 15 000 → 18 000» ценнее записи об UPDATE; расширение Prisma не знает, кто и зачем; обёртка над действиями не видит транзакцию |
| 3 | Append-only | **Код и цепочка хэшей.** У модуля `journal` нет обновления и удаления (тест); каждая запись хранит хэш предыдущей (SHA-256 от канонического JSON), подмену или пропуск видно. Права на таблицу в базе не делим: на hoster.kz у приложения один пользователь базы | Права по таблицам Plesk не даёт; цепочка дёшева и проверяема |
| 4 | 2FA — для кого | **TOTP для Владельца, по желанию:** включается в «Аккаунте» по QR-коду, плюс 10 одноразовых кодов восстановления. Клиентам — нет: их вход по коду — уже владение телефоном. **Гость демо-админки 2FA не включает:** «Аккаунт» ему закрыт (П1, решение 9), а его 2FA заперла бы настоящего Владельца (уточнено при оформлении) | Обязательная 2FA без восстановления может запереть Владельца в собственной админке |
| 5 | Хранение секрета | **Секрет TOTP — в Аккаунте Владельца, зашифрован ключом из окружения** (`TOTP_KEY`, AES-256-GCM); коды восстановления — хэшами (bcrypt, как пароль). Ключ — только в переменных Plesk и Vercel | Дамп в `C:\gym-transfer` и резервная копия Plesk не должны давать второй фактор |
| 6 | Когда код | **После миграции П2 и этапа 3 (декабрь):** журнал сразу с `clubId`, миграции — под шагом CI «прежний код на новой схеме» | Порядок по карте: П2 → 3 → 2 |
| 7 | Модуль | **`journal` — базовый, никого не импортирует:** тип события, канонический JSON, цепочка, `recordEvent(tx, event)`, чтение и проверка цепочки. Кто действовал (Владелец, Гость, Клиент, система) передаёт вызывающий: роль берётся из сессии модулем `owner` | Как `notifications`: платформа событий, смысл — у модулей-хозяев |
| 8 | Виды событий | **Закрытый список типов** (`tariff.updated`, `trainer.deleted`, `owner.login.failed`…), у каждого — схема данных; в данных — только изменённые поля. Пароли, хэши, секреты и телефоны в журнал не попадают (тест по списку запрещённых полей) | Журнал читают люди: тип — подпись в админке; запрет — чтобы журнал не стал утечкой |
| 9 | Сколько хранить | **365 дней.** Старые записи удаляет попутная уборка (как сброс демо, после `/api/health/ready`); первая оставшаяся запись хранит хэш удалённой предыдущей — цепочка проверяется с неё. В Политике конфиденциальности — абзац о журнале и сроке (из `legal/facts.ts`), там, где журнал работает | Бессрочное хранение — лишние данные; удаление по сроку — не правка журнала |
| 10 | Раздел админки | **«Журнал» в меню «Ещё»:** лента событий с фильтрами по разделу, типу и дате, «было → стало» у правок, кнопка «Проверить целостность». Гость видит журнал (в нём нет персональных данных) | Владелец должен видеть, кто что менял; Гость — что журнал работает |
| 11 | Демо-сброс (П1) | **Журнал не сбрасывается**; сам сброс пишет событие «Демо-данные возвращены» | Append-only важнее чистоты демо; видно, когда был сброс |
| 12 | Вход с 2FA | **Два шага:** пароль верен → короткий подписанный токен «пароль пройден» (5 минут, cookie) → код TOTP или код восстановления → сессия. Неверные коды считаются в общем лимите попыток входа. Окно TOTP — ±1 шаг (30 с) | Обычная схема; лимит закрывает перебор шести цифр |
| 13 | Выключение и потеря телефона | **Выключить 2FA — только с текущим кодом.** Потерян телефон — код восстановления; потеряны и они — сброс разработчиком (SQL в Plesk, runbook `docs/runbooks/owner-2fa.md`), событие в журнале при следующем входе | Сброс без кода — путь атаки; у Владельца без SSH всё равно есть разработчик |
| 14 | Реализация TOTP | **Своя, по RFC 6238 и 4226** (HMAC-SHA1 из `node:crypto`, ~40 строк), тесты — векторы из RFC. QR-код — сервером в SVG через пакет `qrcode` только на странице включения | Зависимость ради 40 строк не нужна (как свой отправщик Sentry, ADR 0010); кодировать QR самим — нет |
| 15 | Измерения | **Покрытие:** каждое меняющее действие админки (сейчас 42) пишет событие — тест перечисляет действия, как `guest-locked.test.ts`. **Подмена:** тест на MariaDB правит запись в обход кода — проверка цепочки находит её. **TOTP:** векторы RFC. **Память двойника:** медиана пика — не выше базы после этапа 3 + 5 МБ. **Проверка цепочки** 10 000 записей — меньше секунды | DoD этапа |
| 16 | Термины | **«Журнал действий»** — append-only список событий Клуба; **«Двухфакторный вход»** — вход Владельца паролем и кодом из приложения | В GLOSSARY — как названия разделов админки |
| 17 | Прод | **Как остальные этапы:** код в Лаборатории; на hoster.kz — только релизом по решению Владельца, вместе с `TOTP_KEY` в Plesk и обновлённой Политикой | Прод заморожен на `v1.0.0` |

Решения оформлены в ADR: [0023](../adr/0023-journal-domain-events-hash-chain.md) (журнал: доменные события в транзакции, цепочка хэшей, срок хранения), [0024](../adr/0024-owner-totp.md) (двухфакторный вход Владельца).

## Список PR (черновик)

Каждый PR — короткая ветка, мерж только по слову Владельца репозитория. Код — после этапа 3.

1. **Модуль `journal`:** таблица `JournalEvent` (`clubId`, тип, кто, данные, хэш, хэш предыдущей), `recordEvent(tx, …)`, канонический JSON, проверка цепочки; тесты, включая подмену на MariaDB.
2. **События модулей:** Тарифы, Тренеры и часы, Направления, Отзывы, Фото, Настройки сайта, Клуб, Записи (отмена Владельцем), уведомления (повтор, «решено»), Аккаунт (вход, выход, пароль). Тест покрытия всех меняющих действий и запрещённых полей.
3. **Раздел «Журнал»:** лента с фильтрами, «было → стало», проверка целостности; попутная уборка старше 365 дней; абзац в Политике.
4. **TOTP:** домен (RFC 6238, векторы), шифрование секрета (`TOTP_KEY`), коды восстановления; поля 2FA у Аккаунта Владельца. **Домен сделан раньше этапа, 14 ноября** (без базы и интерфейса): `src/modules/owner/domain/totp.ts` — HOTP/TOTP, base32, проверка ±1 шаг с защитой от повтора принятого шага, ссылка otpauth; `totp-secret.ts` — ключ `TOTP_KEY` (32 байта base64), AES-256-GCM с форматом `v1.`, 10 кодов восстановления «XXXX-XXXX» без похожих знаков. Тесты — векторы RFC 4226 (приложение D), RFC 6238 (приложение B, SHA-1/256/512) и RFC 4648. Осталось на этапе: поля у Аккаунта Владельца, хэши кодов (bcrypt), шифрование в сервисе.
5. **Вход в два шага и «Аккаунт»:** включение по QR, выключение с кодом, коды восстановления; runbook `owner-2fa.md`.
6. **Закрытие:** C4, замер «после», неделя в Лаборатории, ретро.
