# Этап 7: нагрузка и кэш (план)

Начат 13 ноября 2026 (grilling, решения 1–13, везде принят рекомендованный вариант). Инженерная суть из `docs/engineering-roadmap.md`: нагрузка и кэш (по желанию, после этапа 5). Термины — `GLOSSARY.md`.

## Решения

| # | Вопрос | Решение | Почему |
|---|---|---|---|
| 1 | Цель | **Модель мощности.** Найти «колено» — сколько запросов в секунду смеси выдерживает пакет для хостинга на лимитах hoster.kz (256 МБ, 1 CPU, MariaDB 10.4) при p95 ≤ 1 с, без 5xx и при RSS ≤ 230 МБ. Затем кэшем сдвинуть его вправо и закрепить порог в CI | Кэш без замера колена — гадание. Итог этапа — фраза «хостинг выдерживает N запросов в секунду с запасом X» под охраной CI |
| 2 | Инструмент | **k6 в отдельном Docker-контейнере** рядом с прод-двойником: сценарии, ступенчатое наращивание, пороги. Скрипт двойника остаётся для памяти и холодного старта | Генератор нагрузки не должен жить в одном Node с измеряемым сервером |
| 3 | Профиль | **Доли маршрутов — из строк доступа Лаборатории за неделю** (JSON-логи, ADR 0009). **Сценарий Клиента — руками:** вход по демо-коду → Окна Тренера → Запись → отмена | В Лаборатории Записей мало, а это самый тяжёлый путь: расчёт Окон и транзакция с блокировкой |
| 4 | Механизм кэша | **Кэш данных Next с тегами** (`unstable_cache` + сброс по тегу), только для того, что колено покажет узким местом. Сброс: из серверных действий админки — `updateTag` (сразу, «видно своё изменение»; `revalidateTag` с профилем `max` отдал бы старое, а без профиля в Next 16 устарел), вне действий (попутные проверки) — `revalidateTag(tag, { expire: 0 })`. `unstable_cache` в Next 16 — прежний API (документация советует `use cache`), он работает; переход — вместе с Cache Components, если до них дойдёт (уточнено 13 ноября по документации Next 16.4). Кандидаты — то, что кабинет читает на каждом запросе: Клуб, Настройки сайта, Тренеры, Тарифы. **Админка всегда читает базу напрямую** | Работает и в standalone (диск), и на Vercel (общий кэш); `"use cache"` требует `cacheComponents` — смену всей модели отрисовки (ISR-главная, страницы ошибок ADR 0013) |
| 5 | Когда код | **После этапа 5** «SLO-панель, алерты», как в карте этапов | Колено — вход в бюджет ошибок и алерты |
| 6 | Ожидаемая нагрузка зала | **Оценка пика — 2 запроса в секунду** (вечерний наплыв после поста в Instagram: десятки человек на сайте за минуту). **Цель — колено не ниже 10× пика, 20 запросов в секунду смеси** | Настоящей статистики прода нет: боевой сайт снаружи никто не опрашивает (ADR 0005). Запас 10× закрывает ошибку оценки |
| 7 | Где нагружаем | **Только прод-двойник в CI и локально.** Лабораторию не нагружаем: это SLO, деньги и чужие замеры этапов. Боевой сайт — никогда | Колено нужно хостингу, а не Vercel |
| 8 | Что в CI | **На каждом PR — короткая проверка на целевой скорости:** 20 запросов в секунду смеси 60 секунд, пороги p95 ≤ 1 с, 0 ошибок 5xx, RSS ≤ 230 МБ. **Поиск колена (ступени до отказа)** — еженедельно по расписанию и вручную; отчёт — артефакт и строка в журнале этапа | Полный поиск — минуты CI; на PR достаточно «не хуже цели» |
| 9 | Поведение за коленом | **Сначала замер:** что ломается первым — p95, 5xx или память (OOM). Если OOM раньше двойного колена — отдельный PR: ограничение запросов в работе в `start.cjs` (счётчик над `http.Server`, сверх лимита — 503 с `Retry-After`) | Процесс, убитый за память, хуже очереди: Passenger поднимает его заново с холодным стартом |
| 10 | Холодный старт под нагрузкой | **Отдельный сценарий:** нагрузка на только что запущенный процесс (как после сна Passenger) — p95 первой минуты | Холодный старт — отдельный SLI (ADR 0011); под нагрузкой он хуже, чем в одиночку |
| 11 | Запросы к базе | **Счётчик запросов на страницу** — в строке доступа (`db_queries`) через расширение клиента Prisma; замер «до/после» кэша по кабинету и главной | Кэш должен убирать запросы, а не только миллисекунды |
| 12 | Измерения | Колено (запросов/с) до и после кэша; p95 и RSS на целевых 20 запросах/с; запросов к базе на кабинет и главную; p95 первой минуты после холодного старта | DoD: «до/после» |
| 13 | Решения | **ADR 0025** — модель мощности: k6 рядом с двойником, цель 10× оценки пика, проверка на целевой скорости в CI, кэш данных с тегами только по замеру | Чтобы порог в CI не выглядел случайным числом |

Решения оформлены в ADR [0025](../adr/0025-capacity-model-k6-twin.md).

## Список PR (черновик)

Каждый PR — короткая ветка, мерж только по слову Владельца репозитория. Код — после этапа 5.

1. **Профиль из логов:** скрипт долей маршрутов по строкам доступа Лаборатории; счётчик запросов к базе в строке доступа.
2. **k6 рядом с двойником:** сценарии Посетитель, Клиент, Владелец; ступени до отказа; отчёт «колено» — замер «до».
3. **Проверка на целевой скорости в CI** (20 запросов/с, 60 с) и еженедельный поиск колена (`schedule` + вручную).
4. **Кэш данных по узким местам замера** (теги; `updateTag` в действиях админки рядом с `revalidateSite()`, `revalidateTag(…, { expire: 0 })` в попутных проверках); тест «правка в админке видна в кабинете сразу».
5. **Ограничение запросов в работе** — только если за коленом первым приходит OOM (решение 9).
6. **Закрытие:** замер «после», runbook «что делать, если колено ниже цели», ретро.
