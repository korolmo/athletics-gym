# Выкатка и миграции базы

Схема базы меняется только миграциями Prisma (`prisma/migrations/`, в git). `prisma db push` на боевой базе не используем.

## Команды

| Команда | Что делает | Где запускать |
|---|---|---|
| `npm run db:migrate:dev -- --name <имя>` | Создаёт новую миграцию из изменений `schema.prisma` и применяет её | Только локальная или отдельная dev-база |
| `npm run db:migrate` | Применяет ещё не применённые миграции (`prisma migrate deploy`) | Боевая база, при выкатке |
| `npm run db:status` | Показывает, какие миграции применены | Любая база |
| `npm run seed` | **Удаляет** Залы, Тарифы и Тренеров и заводит заново из прайса | Только пустая или тестовая база |

Все команды работают с базой из `DATABASE_URL` / `DIRECT_URL` в `.env`. Перед запуском проверьте, на какую базу они смотрят.

## Миграции

| Миграция | Что в ней |
|---|---|
| `20261007000000_init` | Базовая (baseline): схема этапа 0 — Залы, Тарифы, Тренеры. На боевой базе уже есть, её нужно только **пометить** применённой. |
| `20261008000000_login_attempts` | Новая таблица `LoginAttempt` — неудачные попытки входа в админку (лимит перебора пароля). Существующие таблицы не трогает. |

## Выкатка ветки `refactor-security` на production — один раз

Превью и боевой сайт сейчас на одной базе (Франкфурт), поэтому шаги 2–3 меняют боевую базу. Они только добавляют: создают служебную таблицу миграций и пустую таблицу `LoginAttempt`. Текущий код на них не смотрит, сайт во время шагов работает.

1. **Локальный `.env` — на боевую базу.** В `DATABASE_URL` и `DIRECT_URL` должны стоять строки Франкфурта (те же, что в `.env.preview`). Проверка: `npm run db:status` должен показать хост `...eu-central-1...`.
2. **Baseline** — сказать Prisma, что базовая схема уже на месте (данные не меняются):
   ```powershell
   npx prisma migrate resolve --applied 20261007000000_init
   ```
3. **Применить новые миграции:**
   ```powershell
   npm run db:migrate
   ```
   Ожидаемый вывод: `Applying migration 20261008000000_login_attempts`, затем `All migrations have been successfully applied`.
4. **Проверить:** `npm run db:status` → `Database schema is up to date!`
5. **Merge PR в `main`** и production-деплой.
6. **После деплоя:** войти в админку заново (формат куки сессии изменился, старые входы недействительны) и проверить `/ru`, `/kk`.

Если шаги 2–4 пропустить и сразу выкатить код: сайт и админка работают, но лимит попыток входа выключен, а в логах Vercel при каждом входе будет строка «LoginAttempt: таблицы нет». Это запасной режим, а не штатный.

**Откат.** Код — «Promote» предыдущего деплоя в Vercel. Базу откатывать не нужно: старый код новую таблицу не замечает.

## Обычная выкатка дальше

1. Изменили `schema.prisma` → `npm run db:migrate:dev -- --name <что меняем>` на локальной или dev-базе → миграция появилась в `prisma/migrations/` → коммит вместе с кодом.
2. PR, проверки CI, превью.
3. Перед merge: `npm run db:migrate` на боевой базе, затем merge и деплой. Миграции пишем так, чтобы старый код продолжал работать с новой схемой (сначала добавляем, удаляем — следующей выкаткой).

## Что стоит сделать позже

- Отдельная база для превью: сейчас проверка превью меняет боевые данные, а миграцию нельзя обкатать на превью до production.
- Тогда `prisma migrate deploy` можно добавить в сборку Vercel, чтобы миграции применялись автоматически. Пока база общая, это опасно: любой пуш в ветку применил бы миграции к боевой базе.
