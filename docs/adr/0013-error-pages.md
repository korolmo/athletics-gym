# Страницы ошибок: 404 через middleware, технические работы — переменной, статическая 503 — у веб-сервера

Страницы ошибок сверстаны 23 октября 2026 по макетам Stitch (проект 4810510334939218653: 404, 500, 503, «503 Статическая», «Админка — Раздел не найден», «Админка — Ошибка загрузки раздела»; промпты — `design/STITCH-BRIEF.md`). У проекта два корневых layout, сайт и админка, а общего нет (ADR 0001). С такой структурой Next 15 не может отрисовать на сервере `notFound()` и ошибку внутри маршрута. Вместо них приходит пустая оболочка `<html id="__next_error__">`, а браузер потом показывает `global-error`. Поэтому каждый случай закрыт своим способом.

**Решение.**
- **404 сайта.** Middleware знает страницы сайта внутри языка (`src/lib/site-pages.ts`). Любой другой адрес под `/ru` и `/kk` он переписывает на тот же адрес с кодом 404, и его рисует маршрут `[locale]/[...rest]` с параметрами языка. Страница динамическая, чтобы случайные адреса не копились в кэше на диске. Заголовок вкладки задаёт `not-found.tsx` рядом: при коде 404 Next берёт метаданные оттуда. Что список совпадает с папками `src/app/[locale]`, проверяет тест.
- **404 без языка.** На язык переадресуются только главная и страницы сайта (`/` → `/ru`, `/privacy` → `/ru/privacy`). Неизвестный адрес без языка (`/abc`) сразу получает 404: страницу 404 на языке из cookie, адрес в браузере не меняется. До этого он отдавал 307 на `/ru/abc`, и уже там 404. Google переходил по ссылке на шаг дальше, а в Search Console адрес попадал в «Страница с переадресацией» вместо «Не найдено (404)». Адреса с точкой (`/wp-login.php`) middleware не трогает, потому что не может отличить их от файлов в `public/`. Они попадают в `[locale]` с неверным языком и получают 404 от Next без перехода на другой адрес. Язык 404 зависит от cookie, поэтому middleware ставит ответам без языка `Vary: Cookie`. У переадресаций заголовок доходит до браузера. У самой страницы 404 Next 15.5 заменяет `Vary` своим (`build/templates/app-page.js`), но её ответ идёт с `Cache-Control: private, no-store`, так что ни CDN, ни браузер его не сохраняют. Это проверяет прод-двойник.
- **500 сайта.** Статические страницы (`/ru`, `/kk`, документы), упавшие при первой сборке в кэш, Next отдаёт из Pages Router: это `src/pages/500.tsx`, код 500, в кэш не попадает, и следующий запрос собирает страницу заново. Ошибки при переходах в браузере и упавший layout ловит `app/global-error.tsx`. Обе страницы показывают двуязычную страницу без базы. Динамические страницы сайта (`[...rest]`, `maintenance`) сбой базы обрабатывают сами. **Своей `error.tsx` у сайта нет.** Прод-двойник показал, что при сбое базы во время первой сборки Next кладёт отрисованную `error.tsx` в ISR-кэш как обычную страницу с кодом 200. Тогда вместо главной до часа висела бы «Ошибка 500», а Google получал бы её с кодом 200. Макет 500 с кодом ошибки (`digest`) остался только в админке, где страницы динамические.
- **503 «Идут технические работы».** Включается `MAINTENANCE_MODE=1`. Middleware отдаёт `/<язык>/maintenance` с кодом 503 и `Retry-After: 600` на любой странице сайта. Админка, API и Фото продолжают работать.
- **Статическая 503.** Файл `public/errors/503.html` на двух языках. Если приложение не запущено, его отдаёт веб-сервер хостинга (`docs/hosting-plesk.md`, раздел 10). Файл собирает `npm run errors:build` из словарей, а тест следит, чтобы он не устарел.
- **Админка.** Содержимое раздела обёрнуто в `<Suspense>`. Шапку и меню отрисовывает сервер, а `not-found.tsx` или `error.tsx` раздела показывает браузер. Код ответа у таких страниц 200: это страницы только для Владельца, закрытые от индексации.
- **Контакты на страницах ошибок.** Номер зала есть только в Настройках сайта, то есть в базе. Поэтому 503 показывает WhatsApp и телефон, только если база ответила, а страницы 500, статическая 503 и страница при недоступной базе ведут в карточку зала в 2ГИС.

## Considered Options

- **Общий корневой `app/layout.tsx`** — переделка ADR 0001: у сайта и админки разные шрифты, `lang` и метаданные.
- **`global-not-found.js` (экспериментальный флаг Next 15.4+)** — работает только для адресов, которых нет среди маршрутов. Для `notFound()` внутри маршрута он не срабатывает.
- **`[locale]/error.tsx` по макету 500 (с кодом ошибки и «Попробовать снова»)** — была в PR #52 и убрана: в ISR-кэш она попадает с кодом 200 (см. «500 сайта»).
- **Заголовок с путём от middleware + `[locale]/not-found.tsx`** — `not-found` Next рисует заранее для каждой страницы сегмента, и `headers()` в нём сделал бы главную динамической. К тому же серверная отрисовка `notFound()` всё равно не работает.

## Consequences

- Новая страница в `src/app/[locale]` добавляется в `SITE_PAGES`, иначе она начнёт отдавать 404. Пропуск ловит тест.
- У папки `src/pages` есть побочный эффект: хуки `usePathname` и `useParams` типизированы как «может быть `null`».
- Цена по памяти. Прод-двойник: 256 МБ, 1 CPU, MariaDB 10.4; обход сайта и админки, затем фаза ошибок. В фазе ошибок ломается таблица Настроек и чистится кэш страниц: `/ru`, `/kk` и документы идут в 500 через `pages/500`, плюс 404 `/ru/nope`, `/kk/nope`, `/abc` и `/admin/nope`. Ветка и `main` 07db571 мерились одним и тем же скриптом, по одному прогону.

  | RSS, МБ | `main` | ветка PR #52 | разница |

  Порог — 230 МБ. В `main` упавшая статическая страница тоже идёт через Pages Router (стандартный `_error` Next), поэтому `src/pages/500.tsx` почти не добавляет памяти. Прирост — от страницы 404 и новых маршрутов. Холодный старт в CI: первый `/ru` через 1,7 с, в `main` — 2,0 с.
- Статическую 503 нужно один раз подключить в Plesk. Делается это только в окно выкатки по решению Владельца, потому что боевой сайт заморожен на `v1.0.0`.

## Технический долг

Решение тактическое. У трёх обходов одна причина: два корневых layout, сайта и админки, без общего.

1. **Список страниц в middleware** (`SITE_PAGES`). Каждую новую страницу под `[locale]` нужно вписать вручную, а забытую ловит только тест.
2. **`src/pages` ради одной страницы 500.** Второй роутер в сборке. Из-за него `usePathname` и `useParams` типизированы как «может быть `null`».
3. **`<Suspense>` в админке.** Её 404 и ошибки рисует браузер, поэтому код ответа у них 200, а не 404 или 500.

**Пересмотреть на этапе 6** («Модули с проверяемыми границами», `docs/stages/stage-6-modules.md`). Вариант решения: один корневой `app/layout.tsx` с группами `(site)` и `(admin)`, у каждой свои шрифты, `lang` и метаданные. Тогда `notFound()` и `error.tsx` снова рисуются на сервере, и все три обхода можно убрать. Долг записан в `docs/engineering-roadmap.md`, раздел «Известный технический долг».
