# Модули по сущностям с границей через index.ts, проверка — dependency-cruiser в CI

До этапа 6 код делился только по слоям: `lib/domain` → `lib/validation` → `lib/services` → server actions. Слои соблюдались, но между сущностями границ не было: сервис Фото брал `SETTINGS_ID` из сервиса Сайта, Тренеры и Направления сами удаляли файлы Фото, главная читала все таблицы через один `services/site.ts`. Этап П2 (несколько Клубов) требует изоляции данных по сущностям, а границу, которую никто не проверяет, рано или поздно нарушат. Решение принято на grill-with-docs 6–7 ноября 2026 (`docs/stages/stage-6-modules.md`, решения 3–17).

**Решение.**
- **Модуль — сущность (или группа сущностей) из GLOSSARY, внутри модуля — те же слои.** Код модуля лежит в `src/modules/<имя>/` (`domain`, `validation`, `service`, `presentation`, `index.ts`). Модули: Фото (`photos`), Тарифы (`tariffs`), Тренеры (`trainers`), Направления (`directions`), Отзывы (`reviews`), Обращения (`contacts`), Сайт (`site`), Аккаунт Владельца (`owner`), Главная (`home`).
- **Снаружи модуль виден только через свой `index.ts`** (`@/modules/<имя>`) — и для интерфейса, и для других модулей.
- **Направление зависимостей:** Фото — базовый модуль, о других не знает. Тренеры зависят от Тарифов, обратно — нет. Главная собирает все модули, её не импортирует никто. Событий между модулями нет до этапа 2 (журнал действий).
- **Платформа — `src/lib`** (db, логи, i18n, SEO, юридические тексты, помощники админки: `guard`, `db-errors`, `result`, `revalidate`): модули её импортируют, она модули — нет.
- **Интерфейс остаётся в `app/` и `components/`** (маршруты Next обязаны жить в `app/`) и ходит в модули только через `index.ts`.
- **Проверка — dependency-cruiser** (`.dependency-cruiser.cjs`, `npm run deps:check`, job CI «Dependency boundaries»): слои, единственный путь к Prisma, циклы, `index.ts`, Главная наверху, платформа под модулями. Граф папок (Mermaid) — в сводке каждого прогона CI и в артефакте `deps-graph`.
- **Ввод постепенный:** нарушения на входе записаны в `.dependency-cruiser-known-violations.json` (`npm run deps:baseline`) и проверку не валят; новое — ошибка. Модули переносятся по одному на PR (Фото → Тарифы → Тренеры → Направления → Отзывы → Обращения → Аккаунт Владельца → Сайт → Главная), каждый убирает свои строки, в конце этапа список пуст.

**На входе (7 ноября 2026, `main` + PR #58): 4 известных нарушения** — `photos → site`, `site-settings → site`, `account → owner-account` (сервисы разных сущностей) и цикл `domain/site-settings.ts ↔ site-settings.defaults.ts` (через импорт типа). Пока файлы лежат по слоям в `src/lib`, границу сущностей можно проверить только между файлами `services/*`; правила модулей включены сразу, но срабатывают по мере переноса.

## Уточнения при переносе Фото (PR 4, 7 ноября 2026)

- **Второй публичный вход — `client.ts`** (`@/modules/<имя>/client`): только то, что безопасно для браузера (правила домена, код для браузера). `index.ts` серверный (`server-only`), и клиентский компонент на нём роняет сборку. Правила `module-via-index-*` разрешают оба файла.
- **Сервисы ещё не перенесённых сущностей** (`src/lib/services/*`, кроме `health.ts`) — «модули в ожидании»: им временно можно импортировать модули через `index.ts`. Исключение уходит вместе с папкой в PR «Главная».
- **Платформа получает модуль аргументом.** `lib/services/health.ts` не импортирует Фото: маршруты `/api/health*` берут `photoStorageHealth` из `@/modules/photos` и передают в `getHealth` / `getReadiness`.
- **Граница по данным проверяется тестом.** Сервис Фото пишет пути в таблицы Тренера, Зала, Направления и Настроек сайта — импорты этого не показывают. `src/modules/photos/tables.test.ts` держит список таблиц, которые трогает модуль: своя — Галерея, чужие — до переноса владельца. Каждый PR модуля-владельца забирает своё место для Фото и вычёркивает таблицу; в конце у Фото только Галерея.
- **Правило `photos-knows-no-one`** делает видимой связь Фото → Тарифы (`HALLS` в правилах Фото — место «Плакат прайса Зала»): раньше она пряталась внутри `src/lib`. Уйдёт вместе с местом в PR Тарифов.

## Места для Фото (PR 5, Тарифы, 7 ноября 2026)

- **Место для Фото ведёт модуль-владелец.** Фото объявляет интерфейс `PhotoSlot` (`exists`, `set`, `clear`, `paths`); владелец реализует его над своей таблицей — первым стал «Плакат прайса» (`pricePosterSlot` в модуле Тарифы, путь в `Hall.pricePoster`). Фото выдаёт путь, кладёт файл, убирает прежний и брошенные; владелец только хранит путь.
- **Места собирает слой приложения** — `app/admin/(protected)/photos/slots.ts`, действия раздела «Фото» передают их сервису. Так же, как проверка готовности получает хранилище от маршрутов: зависимость идёт сверху вниз, Фото о владельцах не знает.
- **Защита от забытого места:** места владельцев перечислены в `OWNED_KINDS` сервиса Фото. Без переданного места загрузка в него отклоняется, а уборка пропускается — иначе файлы владельца сочлись бы брошенными и удалились.
- **Проверка id места — у владельца:** домен Фото проверяет только формат (`hall:<id>`), есть ли такой Зал — `pricePosterSlot.exists` (по списку Залов и по базе).
- Следующие владельцы (Тренеры, Направления, Сайт) повторяют то же: своё место, строка в `slots.ts` и `OWNED_KINDS`, таблица вычёркивается из `tables.test.ts`.

## Связи по данным между модулями (PR 6, Тренеры, 7 ноября 2026)

- **Таблицу пишет только её модуль.** Если действию нужна запись в чужую таблицу в одной транзакции, модуль-хозяин отдаёт невыполненный запрос Prisma (`moveTrainerTariffs` в Тарифах), а вызывающий кладёт его в свою `$transaction`.
- **Обратное направление — через слой приложения.** Тарифам при сохранении персонального Тарифа нужен Зал Тренера, но Тарифы не знают Тренеров: `saveTariff` принимает `TrainerHallLookup`, действие админки передаёт `trainerHall` из модуля Тренеры.
- **У каждого модуля — тест таблиц** (`tables.test.ts` на общем `src/lib/testing/module-tables.ts`): список моделей Prisma, к которым модуль обращается. Чужая таблица в списке — либо временная (Фото до переноса владельцев), либо ошибка.

## Модули поверх остальных (PR 8, Отзывы, 7 ноября 2026)

- **Юридические документы — модуль `legal`** (Политика конфиденциальности, Пользовательское соглашение), как и Главная — поверх остальных: числа в текстах (лимиты Отзывов, сроки хранения, cookie) он берёт из правил модулей. Правило `top-modules`: `home` и `legal` не импортирует ни один модуль.
- **Обратная потребность — через слой приложения.** Отзывам для Согласия нужна дата редакции Политики: `createVisitorReview` принимает её аргументом, действие сайта передаёт `LEGAL_UPDATED.privacy`.
- **`revalidateSite()` — слой приложения** (`src/app/admin/revalidate.ts`): его вызывают только действия админки, а ему нужны адреса страниц всех модулей, в том числе юридических.

## Аккаунт Владельца — базовый модуль (PR 10, 7 ноября 2026)

- **`requireOwner` переехал из платформы (`lib/admin/guard`) в модуль `owner`** вместе со входом, сессией, лимитом попыток и сменой пароля: проверка доступа опирается на версию сессии в Аккаунте Владельца, а платформа не может импортировать модуль. Все модули берут `requireOwner` у `owner`, как файлы у Фото; `owner` о них не знает. Правило `photos-knows-no-one` разрешает Фото только этот модуль.
- **`client.ts` модуля `owner` — без `server-only`**: middleware читает cookie сессии (Web Crypto). Правила входа на `node:crypto` — только в `index.ts`.
- **Хэш адреса клиента — платформа** (`src/lib/ip-hash.ts`): им пользуются лимит входа, антиспам Отзывов и счётчик Обращений.
- **Платформенный `getHealth` получает проверку Владельца аргументом** от маршрута `/api/health`, как и хранилище Фото.

## Сайт (PR 11, 7 ноября 2026)

- **У Фото — только Галерея.** Последние места (Фото первого экрана и Женского зала) ведёт модуль Сайт (`heroPhotoSlot`, `womenPhotoSlot`, пути в Настройках сайта). `OWNED_KINDS` — все места, кроме Галереи; `tables.test.ts` Фото — одна таблица.
- **Платформа описывает нужные ей данные сама.** `lib/seo.ts` строил JSON-LD по типу `SiteContent` модуля Сайт; теперь у него свой `SeoSiteContent` — только нужные поля, `SiteContent` подходит по форме.
- **Модель отдельно от правил.** Блоки, колонки показа и типы записей Настроек — в `site-settings.model.ts` без импортов: правила и начальные значения зависят от модели, а не друг от друга (цикл `site-settings ↔ defaults` убран).
- **Нарушений на 7 ноября — 0.** Временное исключение для «модулей в ожидании» держится только ради сборщика Главной (`lib/services/site.ts`) — уйдёт в PR «Главная».

## Considered Options

- **Оставить деление по слоям, проверять только слои.** Дёшево, но сущности остаются склеенными, и П2 придётся резать тот же код под давлением изоляции данных.
- **Модули — шаблоны путей в конфиге, файлы остаются в `lib/<слой>/`.** Нет большого переноса, но граница невидима в дереве файлов, а правило «файл → модуль» по имени неоднозначно (`tariff.ts` и `tariffs.ts`, `site.ts` и `site-settings.ts`, три файла Аккаунта Владельца).
- **Модули общаются событиями** (Тренер удалён → Фото убирает файлы). Развязывает сильнее, но требует шины и журнала — это этап 2. Сейчас прямой вызов публичной функции Фото через `index.ts` проще и проверяем.
- **Включить правила сразу ошибкой.** Первый PR либо красный, либо вынужден переносить всё сразу — против trunk-based и маленьких PR.

## Consequences

- Новый код сущности — сразу в её модуль; импорт `@/lib/services/…` из нового кода — повод остановиться.
- `npm run deps:check` входит в проверки перед коммитом наравне с lint и typecheck.
- `deps:baseline` перезаписывают только в PR, который убирает нарушения: число известных нарушений не должно расти (видно в сводке CI).
- Перенос не должен увеличить память прод-двойника (пик ~197 МБ при пороге 230) и JS для браузера на `/ru` (125 kB) — сверяется в PR закрытия этапа.
