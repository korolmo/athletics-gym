# Запись к Тренеру: двойную Запись запрещает база, уведомления идут через transactional outbox

Статус: proposed (7 ноября 2026, grill-with-docs; `docs/stages/stage-1-cabinet.md`, решения 8–12, 19–20).

Клиент записывается к Тренеру в свободное Окно, и Запись подтверждается сразу. Двое Клиентов могут нажать «Записаться» на одно Окно одновременно, а один Клиент может нажать дважды (двойной клик, повтор после обрыва сети). Владелец должен узнать о новой и отменённой Записи, даже если Telegram в этот момент недоступен. Прежний этап 1 («заявка на Пробное посещение + уведомление») ставил ту же инженерную задачу на учебном примере. Здесь она настоящая.

## Решение

- **Окна не хранятся.** Модуль `schedule` вычисляет их: недельный шаблон часов Тренера (задаёт Владелец) минус исключения минус Записи. Хранится только то, что ввёл человек.
- **Гонку решает база.**
  - Уникальный индекс у Записи по Тренеру и началу, только для действующих Записей. Отменённая Запись освобождает Окно: при отмене поле индекса обнуляется, потому что в MariaDB 10.4 нет частичных индексов.
  - Нарушение индекса превращается в ответ «Окно уже занято», а не в ошибку 500.
  - Проверка «Окно свободно» в коде остаётся только для удобства Клиента, гарантию даёт индекс.
- **Повтор безопасен.**
  - Форма «Записаться» несёт ключ идемпотентности, его создаёт браузер при открытии формы. Повтор с тем же ключом возвращает уже созданную Запись.
  - Лимит «не больше 3 будущих Записей» и срок отмены (12 часов) — константы правил домена в модуле `bookings`.
- **Transactional outbox.**
  - Событие («Запись создана», «Запись отменена») пишется в таблицу outbox в той же транзакции, что и Запись: нет Записи без события и события без Записи.
  - Отправщик забирает события по cron (GitHub Actions вызывает защищённый маршрут) и шлёт их Владельцу в Telegram-бот. В Лаборатории — тестовый чат.
  - Ретраи с растущей паузой. После N неудач событие уходит в dead-letter и видно в админке, оттуда его можно отправить ещё раз.
  - Доставка «хотя бы один раз»: у события свой id, и повтор сообщения Владелец увидит как то же событие.
- **Модуль `notifications`** — платформенный: outbox, отправщик, адаптер Telegram. О модулях не знает: событие ему передаёт сервис-хозяин запросом в своей транзакции, как сейчас `moveTrainerTariffs` (ADR 0015).
- **Время** — в UTC. У Клуба есть часовой пояс (`Asia/Qyzylorda`), шаблон Окон и показ — в поясе Клуба.

## Considered Options

- **Проверка «свободно» и вставка в коде, без индекса.** Две параллельные транзакции обе видят свободное Окно — классическая гонка. Блокировка `SELECT … FOR UPDATE` работает, но держит строки и зависит от уровня изоляции. Индекс проще и проверяется тестом.
- **Хранить Окна строками и «занимать» их.** Окна пришлось бы создавать заранее и пересоздавать при каждой правке шаблона. Вычисление из шаблона не требует фоновой работы.
- **Отправлять в Telegram сразу из действия.** Если Telegram недоступен, уведомление теряется, а если отправка прошла, а транзакция откатилась — Владелец получит уведомление о Записи, которой нет.
- **Очередь (Redis, SQS).** Нужен ещё один сервис. На hoster.kz (256 МБ, без фоновых процессов) его нет, а outbox работает на той же MariaDB.

## Consequences

- Измерение этапа: нагрузочный тест — 50 параллельных записей на одно Окно дают ровно 1 Запись; доля событий, доставленных за 5 минут; число dead-letter за неделю.
- Cron GitHub бывает редким (этап 0, ADR 0014), поэтому задержка уведомления — до интервала cron. Для Владельца это допустимо, для SLO доставки — учитывается в цели.
- На hoster.kz отправщик тоже вызывается извне по cron, процесса в фоне нет.
- Событийная модель здесь — первый шаг к журналу действий этапа 2.
