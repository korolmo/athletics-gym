## Ретро

1. **Сработало:** прод-двойник в CI дал общий язык для решений: Sentry SDK и холодный старт решены цифрами, а не мнением.
2. **Сюрприз:** Vercel вызывает обработчик Next в обход `http.Server`. Перехват `'request'` на Vercel молчал, и это показал только счётчик в `/api/health`. Проверять наблюдаемость нужно в обеих средах, а не по тестам.
3. **Мониторинг окупился в первый же час:** нашёл ложные 503 readiness на холодном старте и артефакты самой синтетики (DNS/TLS раннера, тревога на двух точках).
4. **Не сделано:** UptimeRobot (алерты в Telegram) перенесён на этап 5, «SLO-панель, алерты, постмортемы»; до него тревога — только письмо GitHub о красном «Monitor Lab» при быстром выгорании бюджета. `VERCEL_TOKEN` задан вечером 17 октября: до этого Лаборатория выкатывалась вручную из CLI, теперь — `lab.yml`. Environment `production` с ревьюером настраивает владелец репозитория. CLI `vercel logs` не транслировал логи, проверка шла через `/api/health`.
5. **Дальше:** этап 6 (границы модулей); метка холодного запроса от сервера, если холодные старты начнут съедать бюджет; неделя наблюдения Лаборатории перед закрытием этапа (Definition of Done).

**Холодные старты.** Прогоны идут в среднем раз в 3 часа, ни один не пришёл на тёплый экземпляр функции (интервал меньше 15 минут не встретился ни разу). Значит, все 52 проверки `/api/health/ready` — холодные: медиана 1,4 с против 0,2–0,4 с у тёплого. Страницы `/ru` и `/kk` этого почти не чувствуют: их отдаёт кэш CDN (HIT или STALE в 100 случаях из 104). Отдельный замер после каждой выкатки `main` (`lab.yml`, шаг Cold start, ADR 0011):

Цель ADR 0011 — холодный старт Vercel ≤ 1,5 с — после выкатки выполняется (0,83–0,93 с). После простоя в несколько часов холодный `/ready` дольше — 1,4 с в медиане, 2,4 с в p95: к запуску функции добавляется первое соединение с TiDB.

**Вывод.** Для посетителя страницы были доступны всю неделю: 104 из 104 ответов 200, 96 % быстрее секунды. SLO не выполнен из-за `/api/health/ready`, и это результат устройства самого измерителя. ADR 0011 исходил из того, что синтетика ходит каждые 5 минут и холодные старты в ней редки. На деле GitHub запускал cron в 40 раз реже, поэтому каждая проверка была холодной. 104 проверки страниц — мало, чтобы утверждать 99,5 %.

### Ретро недели

1. **Сработало:** прод-двойник поймал кэширование ошибки в ISR до того, как оно дошло до кого-то, и держит память в рамке (≤ 202 МБ при пороге 230). Превью на каждый PR с эфемерной базой и диагностические превью превратили гипотезы о Vercel в факты за полдня.
2. **Не сработало:** синтетика на cron GitHub — 2 % запланированных прогонов, все проверки readiness холодные, тревога не могла сработать. Цифра SLO недели меряет холодный старт и редкость cron, а не доступность.
3. **Не сработало:** поведение платформы Vercel (подмена 404 и 503) не видят ни тесты, ни двойник, ни мониторинг — нашли руками. В ADR 0013 сначала попал непроверенный вывод «виноваты два корневых layout»: гипотезу записали как факт без воспроизведения на чистом приложении. Файл `lab.yml` дважды не запустился из-за кавычек.
4. **Меняем в процессе на этап 6:**
   - смоук после выкатки — часть Definition of Done каждого этапа: новый путь ответа (ошибки, кэш, переадресация) получает проверку в `smoke.mjs`;
   - вывод о поведении Next или Vercel попадает в ADR только после минимального воспроизведения (чистое приложение или диагностическое превью), а диагностические превью удаляются в конце задачи;
   - workflow проверяется actionlint до пуша (добавить job в CI);
   - повтор подключения к TiDB в seed превью.
5. **Нужно решение до старта этапа 6 — источник синтетических проверок.** Варианты: внешний опрос раз в 5 минут раньше этапа 5 (UptimeRobot уже запланирован, ADR 0011), метка холодного запроса от сервера (ADR 0011, «Considered Options»), тревога «мало прогонов за сутки». Пока цифры SLO в `status.json` и README читаем с этой оговоркой.
