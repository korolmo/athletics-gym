# Выкатка и миграции базы

Схема базы меняется только миграциями Prisma (`prisma/migrations/`, в git; решение — `docs/adr/0003-prisma-migrate.md`). `prisma db push` на боевой базе не используем.

## Какая база где

Баз две, обе — Supabase во Франкфурте (`eu-central-1`). У них один и тот же хост пулера (`aws-1-eu-central-1.pooler.supabase.com`), **различаются они только кодом проекта в имени пользователя** (`postgres.<код>`).

| База | Проект Supabase | Кто с ней работает | Где лежат строки подключения |
|---|---|---|---|
| **Разработка и превью** | `athletics-gym-dev`, код `ptiiovdgxjdcpxlygnrx` | `npm run dev` на компьютере; все превью Vercel (любая ветка) | `.env`; Vercel → Environment Variables → **Preview** |
| **Боевая** | код `vrvupsqjhyhghgikboif` | Только https://athletics-gym.vercel.app | `.env.preview` (имя историческое); Vercel → **Production** |

- Превью больше не на боевой базе: всё, что меняется в админке превью или локально, остаётся в базе разработки и на боевом сайте не видно.
- Данные в базе разработки — из `npm run seed`; их можно свободно менять и пересоздавать.
- **Локальный `.env` на боевую базу не переключаем — ни временно, ни насовсем.** Команды для боевой базы запускаются с явным файлом `.env.preview`.
- Хост в выводе Prisma (`Datasource "db": … at "…"`) у обеих баз одинаковый, по нему базу не отличить. Чтобы убедиться, с какой базой работает команда, смотрите на имя скрипта: без `:prod` — разработка, с `:prod` — боевая.
- Аккаунт Владельца у каждой базы свой: на превью и локально входят с паролем из базы разработки, на боевом сайте — из боевой. Пароли могут отличаться (см. «Аккаунт Владельца»).

## Команды

| Команда | Что делает | База |
|---|---|---|
| `npm run dev` | Локальный сайт и админка | разработка (`.env`) |
| `npm run db:migrate:dev -- --name <имя>` | Создаёт миграцию из изменений `schema.prisma` и применяет её | разработка |
| `npm run db:migrate` | Применяет ещё не применённые миграции | разработка |
| `npm run db:status` | Показывает, какие миграции применены | разработка |
| `npm run seed` | **Удаляет** Залы, Тарифы и Тренеров, заводит заново из прайса и возвращает Настройки сайта к начальным; аккаунт Владельца не трогает | разработка; на боевой откажется |
| `npm run db:status:prod` | Состояние миграций боевой базы (только чтение) | **боевая** (`.env.preview`) |
| `npm run db:migrate:prod` | Применяет миграции к боевой базе | **боевая** (`.env.preview`) |

Скрипты `:prod` — это `dotenv -e .env.preview -- prisma …` (пакет `dotenv-cli`): переменные из `.env.preview` подставляются только на время одной команды. То же без `dotenv-cli`, одной командой PowerShell:

```powershell
# переменные живут только внутри этого вызова и не остаются в окне терминала
powershell -NoProfile -Command "Get-Content .env.preview | Where-Object { $_ -match '^\s*(DATABASE_URL|DIRECT_URL)\s*=' } | ForEach-Object { $k, $v = $_ -split '=', 2; Set-Item ('Env:' + $k.Trim()) $v.Trim().Trim([char]34) }; npx prisma migrate status"
```

Seed на боевой базе по умолчанию не запустится: он узнаёт её по коду проекта в строке подключения и завершится с объяснением. Осознанный запуск — `npx dotenv -e .env.preview -- npm run seed:force-production`; он сотрёт всё, что Владелец поправил в админке, включая тексты и контакты в разделе «Сайт».

## Обычная выкатка

1. **Миграция.** Изменили `schema.prisma` → `npm run db:migrate:dev -- --name <что меняем>` → миграция появилась в `prisma/migrations/` и уже применена к базе разработки → коммит вместе с кодом.
2. **Превью.** Пуш ветки, PR, проверки CI. Превью ветки работает на базе разработки, где миграция уже есть, — на нём можно проверить и схему, и админку, не трогая боевые данные.
   Если миграцию написал кто-то другой или вы на другой машине: `npm run db:migrate` применит её к базе разработки.
3. **Боевая база — перед merge.** `npm run db:status:prod` (только чтение: убедиться, что не применены ровно ожидаемые миграции), затем `npm run db:migrate:prod`.
4. **Merge PR в `main`** и production-деплой.
5. **Проверка** боевого сайта: `/ru`, `/kk`, вход в админку.

**Порядок обязателен: сначала миграция на боевой базе, потом код.** Миграции пишем так, чтобы старый код продолжал работать с новой схемой (сначала добавляем, удаляем — следующей выкаткой): между шагами 3 и 4 боевой сайт работает на старом коде с новой схемой.

**Откат.** Код — «Promote» предыдущего деплоя в Vercel. Базу при добавляющих миграциях откатывать не нужно: старый код новые таблицы и колонки не замечает.

**Если база недоступна.** Вход в админку отклоняется, пока база не ответит («Вход временно недоступен»): лимит попыток хранится в ней. Уже вошедший Владелец тоже ничего не сможет открыть — данные админки в той же базе.

## Аккаунт Владельца

- Аккаунт один и хранится в базе (`Owner`): логин, хэш пароля (bcrypt), версия сессии. У базы разработки и у боевой он свой.
- **Сейчас** аккаунт есть в обеих базах, а `ADMIN_PASSWORD` в Vercel нет ни в Production, ни в Preview: пароль хранится только в базе, меняется только в разделе «Аккаунт».
- **Первый вход.** Пока записи нет, вход сверяется с `ADMIN_LOGIN` / `ADMIN_PASSWORD` и создаёт её. После этого переменные не используются. Если записи нет и `ADMIN_PASSWORD` не задан — войти нельзя никому.
- **Отзыв сессий.** Смена пароля и «Выйти на всех устройствах» увеличивают версию сессии; все выданные раньше куки перестают подходить. Переменной `AUTH_SESSION_VERSION` больше нет.
- **Владелец забыл пароль.** Сброс делает разработчик: задать в Vercel новый `ADMIN_PASSWORD` (Production), передеплоить, удалить запись в таблице `Owner` боевой базы (Supabase → Table Editor) и войти новым паролем — аккаунт создастся заново. Удаление записи гасит и все сессии. После входа сменить пароль в разделе «Аккаунт» и снова удалить `ADMIN_PASSWORD` из Vercel.
- **Превью и локальная разработка.** База разработки у них общая, поэтому аккаунт один на двоих. Если его запись удалить (например, вручную при проверке входа), локально он создастся заново из `.env`, а на превью — только если вернуть `ADMIN_PASSWORD` в переменные Preview. `npm run seed` аккаунт не трогает.

## Хранилище фото (Supabase Storage)

Фото лежат в бакете `media` того же проекта Supabase, что и база: у базы разработки — своё хранилище, у боевой — своё. В базе хранится только путь к файлу (решение — `docs/adr/0002-supabase-storage-for-photos.md`).

**Переменные** — только для сервера, без `NEXT_PUBLIC`. Значения — Supabase → Project Settings → API своего проекта: «Project URL» и ключ `service_role`.

| Переменная | `.env` и Vercel → Preview | `.env.preview` и Vercel → Production |
|---|---|---|
| `SUPABASE_URL` | `https://ptiiovdgxjdcpxlygnrx.supabase.co` | `https://vrvupsqjhyhghgikboif.supabase.co` |
| `SUPABASE_SERVICE_ROLE_KEY` | ключ `service_role` проекта разработки | ключ `service_role` боевого проекта |

- Ключ `service_role` даёт полный доступ к проекту в обход всех правил: не коммитить, не вставлять в чаты, не давать ему имя с `NEXT_PUBLIC`.
- Адрес хранилища попадает в CSP (`img-src`, `connect-src`) и в настройки `next/image` **при сборке**: после добавления или смены `SUPABASE_URL` в Vercel нужен новый деплой.
- Без этих переменных сайт работает как раньше (картинки из `public/`), а раздел «Фото» сообщает, что хранилище не настроено.

**Бакет.** Создаётся и настраивается скриптом (повторный запуск безопасен, файлы не трогает):

| Команда | Проект |
|---|---|
| `npm run storage:setup` | разработка (`.env`) |
| `npm run storage:setup:prod` | **боевой** (`.env.preview`) |

Скрипт делает бакет `media` публичным и задаёт ограничения в самом бакете: только `image/webp`, `image/jpeg`, `image/png`, файл до 5 МБ. Он откажется работать, если `SUPABASE_URL` и `DATABASE_URL` указывают на разные проекты. То же можно сделать руками: Supabase → Storage → New bucket → имя `media`, Public bucket, File size limit 5 MB, Allowed MIME types — три типа выше.

**Как устроена загрузка.** Браузер Владельца сжимает фото (до ~1600 px, WebP) → сервер проверяет сессию, тип и размер и выдаёт подписанную ссылку на один файл с именем-uuid → браузер загружает файл прямо в хранилище → сервер записывает путь в базу и удаляет прежний файл этого места. Через функции Vercel файл не проходит.

**Уборка.** Файл без записи в базе не должен оставаться: при замене, удалении и неудачной записи он удаляется сразу. Загрузки, брошенные на полпути (закрыли вкладку, пропала связь), удаляются при следующей успешной загрузке — если файлу больше часа и на него нет ссылки из базы.

**Seed и Фото.** `npm run seed` Залы обновляет, а не пересоздаёт (Плакаты прайса сохраняются), фон первого экрана, фото Женского зала и Галерею не трогает. Тренеры пересоздаются — их загруженные Плакаты пропадают, файлы подберёт уборка.

## SEO и адрес сайта

| Переменная | Где | Зачем |
|---|---|---|
| `SITE_URL` | Vercel → **Production** (необязательно) | Адрес сайта для canonical, hreflang, sitemap, превью ссылок и разметки. Без неё — `https://athletics-gym.vercel.app`. С доменом .kz меняется только она: `https://<домен>`, без пути и без слэша в конце |
| `GOOGLE_SITE_VERIFICATION` | Vercel → **Production** (необязательно) | Код подтверждения из Google Search Console (способ «Тег HTML», только значение `content`). Задана — на страницах появляется meta-тег |

- После добавления или смены этих переменных нужен новый деплой.
- **В поиск попадает только production.** На превью и локально (`VERCEL_ENV` не равен `production`) страницы отдают `noindex`, заголовок `X-Robots-Tag: noindex`, а `robots.txt` — `Disallow: /`: превью работает на базе разработки и в Google попадать не должно.
- В production `robots.txt` закрывает `/admin` и `/api` и ссылается на `sitemap.xml` (в нём `/ru` и `/kk` с hreflang).
- Картинка-превью ссылок собирается по запросу: `/ru/opengraph-image` и `/kk/opengraph-image`, 1200×630. Адрес на ней — из Настроек сайта. WhatsApp и Telegram запоминают превью ссылки надолго: после смены адреса старая картинка у них может держаться.
- **Переезд на домен .kz:** подключить домен в Vercel → задать `SITE_URL` → деплой → добавить домен в Search Console и отправить `sitemap.xml`. Старый адрес `vercel.app` после этого лучше закрыть переадресацией на новый в настройках доменов Vercel.

## Счётчик Обращений

- Сайт сообщает о нажатии на кнопку связи запросом `POST /api/contact` (`navigator.sendBeacon`). Ответ всегда пустой (204), даже если запись не удалась: переход в WhatsApp от него не зависит.
- В базе — только Канал, Источник, язык и время (`ContactClick`). IP не хранится, cookies не ставятся, сторонних сервисов нет.
- Лимит — 20 нажатий в минуту с одного адреса. Счёт ведётся в памяти сервера по хэшу адреса и в базу не пишется; у каждого экземпляра функции Vercel память своя, поэтому лимит приблизительный — он от накрутки «в лоб», а не точный учёт.
- Нажатия Владельца, пока он вошёл в админку в этом же браузере, не считаются. Чтобы проверить счётчик самому — нажимайте из другого браузера или из окна инкогнито.
- Сводка — главная страница админки: сегодня, 7 и 30 дней; сутки считаются по времени Кызылорды (UTC+5).
